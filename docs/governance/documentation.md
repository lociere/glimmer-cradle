# 文档质量与维护责任

> 范围：内容正确性、可用性与维护标准；实际编辑步骤见文档维护指南。
> 事实依据：当前文档工具、项目授权和文档/协作设计；外部依据见研究记录。
> 维护触发：读者需求、内容 owner、质量门或资料生命周期变化。

## 内容契约

一页先回答一个连贯的问题或任务。说明适用对象、实现/目标状态、所依据的源及何时需要更新；
可以用短导语或头部字段表达，不为满足模板堆空标题。索引明确下一站，正文给出答案、因果或操作成果。

类型是写作目的，不是必须采用的目录数量。具体归属、权威顺序与结构见 [文档架构](documentation-architecture.md)；
完整操作可以保留必要解释和最小示例，精确字段表由一处维护。

| 读者目的 | 有用内容 | 应排除的失败方式 |
|---|---|---|
| 学会并取得第一个成果 | 已知起点、受控步骤、可观察反馈、收尾和继续路径 | 只有安装命令或一次展开全部系统 |
| 完成操作/排障/恢复 | 前置条件、关键判断、命令、输出、失败和恢复 | 只列工具名、忽略副作用或回退 |
| 查询精确事实 | 名称/语义/owner、来源、兼容与限制、最小例子 | 从目标或记忆编造当前值 |
| 理解设计 | 问题、上下文、关系、原因与取舍，连接实现 | 只列路径，或用历史愿望冒充当前 |
| 接手工作/追溯证据 | 候选、授权、实际状态、证据限制、下一动作 | 第二份独立进度或追溯增强旧结论 |

## 事实与措辞

当前陈述核对源码/Schema/manifest/真实 consumer；行为结论需相应运行证据。注明调查或证据的候选/环境；
Git 日期只说明编辑时间，不证明资料仍正确。找不到证据就写具体未知项与核验入口，不能补成既有能力。

目标要求、当前偏差、临时桥接、历史决定与推荐方法分清。要求强度有具体理由：
“必须/不得”用于真实不变量、权限或脆弱操作，“应/可”用于建议与选择。
不把单次失败、工具偏好、外部模板和固定方案数升级为永久要求。

正文使用一致术语和直接技术语言；代码标识符沿用实际名称。较长页面提供能帮助定位的目录/小节，
不按固定行数制造章节。图表须有解释关键关系的文字；示例是核验过的最小 API/命令，不复制真实私人数据。

## 维护和过期

实现 owner 改变事实时，同步其权威页和直接消费者。维护者先判断缺陷在代码、工具、资料还是规则，
有反例才修最小必要内容；不因一次遗漏追加全局加载要求。

职责迁移时保留原 owner 到新 owner 的追溯，先切消费者再删除旧入口。旧决定/证据有价值时进入历史或保留明确日期的记录；
重复导航和无独立知识的壳可合并删除，Git 保存原文。不得改写历史测试结论使其看似覆盖新要求。

重要外部来源记录 URL、版本/commit、借鉴点、适配和限制，放在维护研究页；普通任务不默认加载。
上游重要变化、重复失败、文档漂移或新增模块触发复核，不设置无用途的日历更新或每次全仓重审。
