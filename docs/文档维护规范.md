## 选择正确的文档

| 信息类型 | 唯一归属 |
|---|---|
| Glimmer Cradle 的解释、架构审美、长期不变量与目标形态 | `architecture/blueprint/` |
| 当前结构、边界、运行时关系与质量要求 | `architecture/current/` |
| 源码入口、组装、映射、状态与调试链路 | `architecture/implementation/` |
| Schema、配置键、路径、日志字段、SDK API | `reference/` |
| 开发、排障、发布操作 | `guides/` |
| 未完成工作的顺序与验收 | `roadmap/` |
| 长期架构取舍 | `architecture/decisions/` |
| 已结束阶段或被替代设计 | `history/` |

物理目录分三层：

- [目标物理拓扑](./architecture/blueprint/目标物理拓扑.md) 保存理想完成态；
- [当前物理拓扑](./architecture/current/10-当前物理拓扑.md) 保存当前真实树；
- [物理拓扑差距与迁移地图](./architecture/current/11-物理拓扑差距与迁移地图.md)
  保存主要 Current → Target 动作。

Roadmap 只补充当前 milestone/slice 的完成态子树、实施顺序和删除门，不复制整份 Blueprint。

## 文档头部

除索引页外，文档开头必须说明：

- **范围**：它回答什么，不回答什么；
- **事实依据**：对应代码、Schema、配置或 ADR；
- **维护触发**：改动哪些边界时必须同步更新。

文档更新时间以 Git 历史为准。路线图的 `now.md` 应另外标记本次审阅日期。

## 规范用语

正文采用客观、直接的技术书面语，围绕职责、适用条件、操作和结果组织内容。

- **要求强度**：“必须”表示强制要求，“应”表示推荐做法，“可”表示允许的选择，“不得”表示明确的禁止事项。安全、权限和关键不变量的约束应保持清晰。
- **规则表达**：优先直接说明应采取的行为；按需要补充适用条件、责任主体和验证标准。
- **事实与建议**：区分当前事实、设计决定、推荐做法和待验证假设，并给出相应依据。
- **比较与限制**：方案比较应写明比较维度、适用条件和取舍；限制说明聚焦具体边界及后果。常规规则直接描述当前要求。
- **术语与标题**：同一概念使用一致术语；标题表达主题或职责。机器标识符保留原名，专业缩写在必要时解释。
- **语气与修辞**：采用可核验的陈述，避免反问、拟人化评价、情绪化措辞，以及依赖假设对立观点的论述。
- **时态与指代**：明确当前状态、目标状态和条件状态；长期规范使用稳定指代，任务过程保存在任务记录或历史证据中。

## 写作与校验

1. 先改唯一权威页，再改索引和链接。
2. 结构图使用 Mermaid，并附上说明相同关键关系的可读文字。
3. 活跃长文档若超过约 80 行或包含 6 个以上二级章节，应在头部契约之后提供目录；索引页、短任务页和 `history/` 归档不强制。
4. 示例只保留最小可执行或可验证片段；精确字段链接到 Reference。
5. 合并前检查相对链接、旧路径、旧术语和重复事实。
6. 代码、Schema、配置或脚本改动后，在同一工作内更新对应文档。
7. 新建 Git 分支或新增、重命名标识符时检查 [命名规范](./guides/development/命名规范.md)。

## 完成态物理目录门

涉及 owner、目录、加载入口或安装/运行数据命名空间重组的 milestone/slice，在实现前
必须明确受影响范围的完成态物理目录；普通局部修复、文字修改不要求全仓目标树。结构性变更至少包含：

- 最终真实路径及唯一 owner；
- Current → Target 的 retain、create、move、split 或 delete 动作；
- 被替代旧路径的 consumer-zero 删除门；
- repository source、artifact/package、installed host、runtime data/cache/log/backup
  等不同命名空间；
- 当前入口、构建入口、安装入口和运行数据 owner。

目录树应列出精确路径，可配表格说明 owner 和迁移动作。无法确定最终
路径时，先调查或设计，不开始依赖该未知布局的迁移。实现中必须改路径时，先修订
拥有该决定的权威页并说明理由，再修改代码；只有长期不变量改变才升级 Blueprint/ADR，
局部指令目录调整由对应工作流文档记录。

审查物理变更时分别核对：

1. Target 是否足够精确；
2. Current 是否与基准 Git tree、manifest 和入口一致；
3. 实际改动是否限于当前 slice 声明的路径；
4. 完成后的目录是否达到 Target；
5. 旧路径是否按删除门消失。

历史 milestone 不追溯整改。本规则从生效后的新任务开始执行，并按用户要求用于
[M12](./roadmap/manifests/M12-目标物理清单.md) 与
[M13](./roadmap/manifests/M13-目标物理清单.md)。

## 活跃文档质量门

| 类型 | 最低内容 |
|---|---|
| Reference | 范围、权威来源、事实模型/所有权、变更与兼容规则、验证 |
| Guide | 适用场景、前置条件、步骤、决策/失败分支、验证、文档同步 |
| Roadmap | 成果、范围/非范围、依赖/风险、验收门、归档位置；结构性迁移另含完成态物理目录 |
| Skill reference | 适用任务、判断方法、实施顺序、禁止项、验证或交付检查 |

正文页应具备其文档类型要求的实质内容。仅承担导航的页面归为索引；与其他权威页职责重合的内容应合并维护。

## 文档模板

### Architecture

```md
# 标题

> 范围：
> 事实依据：
> 维护触发：

## 结构与边界
## 不变量
## 运行时关系
## 相关 Reference、Guide 与 ADR
```

### Guide

```md
# 任务名称

> 适用场景：
> 前置条件：

## 步骤
## 失败与恢复
## 验证标准
## 需要同步的文档
```

### ADR

```md
# ADR-XXXX：决策名称

- 状态：proposed | accepted | superseded | deprecated
- 日期：YYYY-MM-DD

## Context
## Decision
## Consequences
## Alternatives considered
## Links
```
