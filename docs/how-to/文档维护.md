# 修改和核实项目文档

> 适用场景：编写、修正、合并、迁移或审查项目资料；源码改动引起的文档同步也使用本页。
> 事实依据：实际源码/Schema/manifest、repo-checks、目标目录契约；质量要求见文档规范。
> 维护触发：编辑、来源核验、导航或检查工具变化。

## 找到要维护的内容

先确定读者需要回答的问题或取得的成果，再读所属页和直接事实源。局部修正无需重读全仓资料。
归属不清时查 [文档架构](../governance/documentation-architecture.md)，质量判断查 [文档规范](../governance/documentation.md)；
Codex 的专项判断可用 [glimmer-documentation](../../.agents/skills/glimmer-documentation/SKILL.md)，本页已给出完整操作，不要求来回跳转。

核对重要陈述对应的实际入口、public export、producer/mapper/consumer 和测试，区分目标、实现与接受状态。
例如旧记忆 repository 路径消失时，要定位真实接替类与调用者；不能仅按文件名猜新位置。
查询配置只看 Schema/默认来源，不打印 secret 值。

## 修改正文与读者路径

更新拥有详细内容的页面，同时修正会因此误导读者的摘要、示例、索引、Skill 和命令引用。
用 `rg` 搜旧名称/路径/字段及同义说法，再查匹配语境；代码示例和历史引用不宜机械全局替换。

操作指南给出起点、步骤中的必要判断、可观察结果、失败/恢复与退出；说明页连接原因与实际边界。
允许短述必要上下文并链接详细 owner，避免多处独立维护长流程，也避免把正文拆成层层转介。

新增或合并前检查已有页的用途、调用者与追溯价值：
有效内容迁入接替页并切链接；有历史价值的原始结论保留归档语境；空壳或重复导航可删除。
运行记录保留原候选和限制，不把历史 PASS 改写成当前验收。

## 文件增删和受控目录

按变化选择，在一个连贯文档/实现批次收束时完成；不把下表当每个小补丁的固定清单：

| 变化 | 必要维护与检查 | 不额外触发 |
|---|---|---|
| 只改正文/已有证据/指令 | 修正文与直接消费者；本批运行 docs、encoding、diff；Skill 变更加 skills | 不重建目录，不重跑无关产品测试；是否更新摘要另看规范源是否变化 |
| execution.json 状态或 nextAction | 同步唯一状态后运行 `pnpm check:docs --write`，生成 status 并完整检查文档 | 不维护第二份状态，不改目标树或产品基线 |
| 文件增删/移动/重命名，或目标清单变化 | 同步 [files.json](../architecture/target/files.json)、路径消费者；运行 docs 与 target-layout 的 `--write`；复核 consumer-zero/历史语境 | 不因新文件路径就重设计架构；未变生成内容不单独制造修订 |
| baseline.lock.json 列出的规范源字节变化（含正文） | 按[摘要锁维护](../governance/architecture-change-policy.md#摘要锁维护)同步受影响摘要及 expectedLock，检查 architecture | 普通事实页/已有 evidence 不在锁内；不批量更新无关规范或产品语义 |
| 生成器/检查器行为或输入契约变化 | 定向工具反例与受影响门；可执行工具变化按最终源码交付要求验证 | 不为纯措辞或只同步摘要值重跑全部工具/产品套件 |

仅正文变化无需重建目录，但若正文恰属受控规范源仍须同步摘要。既有文件路径/owner 不变时不改 files.json。
删除路径时检查活跃消费者已切换，历史引用保留明确语境；不同意图的相似词不当作同一 owner。

改变产品 owner、依赖、协议或安全/数据边界时适用架构决策要求；普通资料重组不顺带推进产品迁移。
不为文档任务重写用户已有 dirty 状态。

## 验证能否使用

在最后一次相关修改后，运行 `pnpm check:docs`、`pnpm check:encoding` 和 `git diff --check`；
改 Skill 时追加 `pnpm check:skills`。检查工具源码变化再运行其定向测试与最终源码门。

`check:docs --write` 先校验结构/状态并写生成视图，随后调用与只读模式相同的 `checkDocs`，其中再次校验结构及本地文件/章节/可达性。
所以它 **exit 0 已覆盖同一输入的 `check:docs`**，无需紧接重复运行。之后文档、清单、状态、链接目标或检查器等相关输入变化才重跑。
失败时可能已经写了视图，应检查 diff 并修复真实原因；失败不能作为已验证证据，也不能假定自动回滚。
`check:target-layout --write` 同样写后检查目标规范；`check:architecture` 已包含普通 target-layout 检查。
同批相同输入下 architecture 通过后不必再单独跑普通 target-layout；`--final` 的实物/Git 集合检查仍是独立最终门。

再实际沿一个代表请求从入口走到答案或成果，核对版本/owner、关键步骤、失败和退出。
命令在临时数据/fixture 中运行；不把真实模型、设备下载、消息、发布或生产切换混入无副作用检查。
不能运行的操作写清环境缺失和保留证据，格式通过不代替事实或行为验证。

当前 `check:docs` 用 CommonMark AST 核对活跃 Markdown 本地文件/章节链接（GFM 标题 slug 约定）、可达性、
docs 精确清单、架构任务依赖/状态与生成视图；包括自页、编码及目录 README 的章节。
不检查远端可用性、HTML 链接/显式 HTML anchor、代码片段和历史正文，也不证明源码事实。
这些部分按受影响内容人工或用相应技术工具复核，不声称脚本覆盖了未检查项目。

## 交付和恢复

报告读者成果、核实/仍未知的事实、迁移与实际检查结果；简单任务可合为一段。
发现漂移先修所属页或工具，反复出现且有证据时再修方法。
撤回时一并恢复正文、路由、清单、生成树和受影响摘要，保留产品数据与用户改动。
