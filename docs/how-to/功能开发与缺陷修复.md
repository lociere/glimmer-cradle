# 功能开发与缺陷修复

适用于既有产品边界内的需求澄清、功能实现、构造/集成或已知缺陷修复。
从用户成果、真实 owner 和已有授权开始；已明确的局部修正直接做，不强制写计划或需求文档。

## 把请求变成可验证行为

未知项会影响实现时，先用最小例子明确参与者、触发、输入、可观察结果和验收条件。
分别看正常/空态、拒权/非法输入、超时/取消、降级、恢复/退出。质量要求具体化：例如哪个请求的延迟、
哪个状态的容量/可访问性、什么数据不能丢；不要只写“高性能/可靠”。问题能从源码、既有 brief 或测试核实就先调查，
只有不可推断且影响实质选择时问用户，同时继续不依赖答案的工作。

领域概念使用[术语表](../architecture/current/09-术语表.md)和[命名规则](../reference/naming.md)；
确认实体身份、值、命令/事件、状态转换与不变量，由谁接纳、提交、读取和撤销。
例如 ConversationAddress 是外部地址，canonical ConversationContext 由正式 owner 解析；不能在 UI/Adapter 新建第二套身份规则。
需要图时画能解决问题的状态/时序/依赖图，不为简单改动建立完整建模文档。

## 定位、构造与集成

检查 Git dirty 并保留非本任务修改。用 `rg` 从实际入口追 producer→owner/port→mapper→consumer、配置、测试和文档。
逻辑职责、运行进程和 workspace/build 单元分别核对：[实现地图](../architecture/implementation/README.md)、
产品/包 manifest、公开 exports、composition、生成器与固定工具链。目标目录不能替代当前 consumer。

在实际 owner 内实现：领域策略通过消费方 Port 接能力，平台 IO 在 App/adapter/main/native，Renderer 消费受控投影。
配置/字段/路径/token 改各自唯一源；新跨语言语义才走[契约变更](Schema与跨进程契约变更.md)，不手写 generated DTO。
库升级/构建配置确认真实 API、锁、运行平台、许可及可重复输入，不靠全局安装或放宽检查掩盖问题。
新增资源明确启动、ready/降级、取消、释放与重试 owner；替换逻辑先切消费者和保护数据，再删除已无消费者的旧路径。

| 变化 | 补充操作 |
|---|---|
| 用户流程、组件、异步状态、视觉 | [UI 指南](前端开发与UI验收.md)，按项目 ui 方法取得真实浏览器成果 |
| 职责、进程、依赖方向或不变量 | [架构性改动](架构性改动.md)，仅涉及 v2 切片时读其任务书 |
| 用户状态、旧目录、事务、备份/恢复 | [数据迁移与恢复](数据迁移与恢复.md)及 services/persistence |
| 认证/授权、路径、网络或上传边界 | [权限审查](审查权限与外部边界.md)，验证接纳和拒绝而非只隐藏 UI |
| CI、固定制品、安装或回滚 | delivery 方法与[打包](客户端打包.md)/[部署](Personal%20Server部署.md) |
| 根因/时序尚不清楚 | investigation 方法与[排障](日志、Trace与DLQ排障.md)，先做能区分假设的实验 |

## 构建、启动与验证

先核实际 package scripts/pyproject 和依赖前置，运行定向类型/测试/构建。`pnpm build`、runtime preparation、
产品启动是不同动作；不为了局部 fixture 默认运行 `pnpm dev`、下载模型或连接外部账号。
需要启动时核对进程、数据根、端口、必需能力和停止 owner；端口/握手不等于业务 ready，退出命令返回也不等于资源已释放。
失败后区分旧产物、环境、缺依赖与产品缺陷；连续无效尝试应改变假设，而非不断扩大 timeout。

按[测试与验收](测试与验收.md)选择直接成果与反例，最终源码交付集中跑根 `pnpm typecheck`、`pnpm build` 及相关门。
可复用证据须匹配源码、输入和环境；未运行/替身/设备/安装分别报告。
事实变化更新所属实现/参考，操作变化更新指南；交付结果、实际证据、残余缺口和恢复影响。
