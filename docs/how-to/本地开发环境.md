# 本地开发环境

> 适用场景：首次在本机配置 Glimmer Cradle 开发环境，或排查依赖/启动环境问题。
> 前置条件：本文命令使用 Windows PowerShell；已安装符合仓库版本要求的 Git、Node.js、pnpm、Python/uv。Linux 交付见产品部署指南，不外推本机设备支持。

首次只想验证代码和一个界面时，准备依赖后使用 [首次受控验证](../tutorials/首次受控验证.md)；
下方完整产品启动会运行 Kernel、Cognition、Desktop 和受管 sidecar，可能触及实际模型、设备或配置资源，先核对本次目标和环境。

## 初始化

```powershell
pnpm install --frozen-lockfile
```

Python 主仓库通过根 `pyproject.toml`/`uv.lock` 统一解析，共享根 `.venv`。在仓库根选择成员：

```powershell
uv sync --inexact --package glimmer-cradle-cognition-worker --package glimmer-cradle-audio-engine --extra dev
```

需要完整语音能力时：

```powershell
uv sync --inexact --package glimmer-cradle-cognition-worker --package glimmer-cradle-audio-engine --extra tts --extra asr --extra dev
```

共享环境日常同步用 `--inexact` 保留已安装的其他成员/Audio extras；精确清理依赖时应先确定完整 package/extra 集合，
再有意选择不带该参数的同步。省略它可能卸掉先前安装、当前选择中未包含的语音依赖。

## 配置

- 普通配置在 `configs/system/`、`configs/characters/<character-id>/`、`configs/extensions/`。
- 密钥只放 `configs/secrets/` 或环境变量。
- 不把 provider key、token、私人模型路径写入文档、示例或日志。
- Avatar/音频/模型路径通过 resolver 和 catalog 处理，不在代码里写本机绝对路径。

## 常用启动与验证

```powershell
pnpm typecheck
pnpm build
pnpm dev
```

三条命令属于不同阶段：`pnpm build` 是当前源码/资产构建；`pnpm prepare:runtime` 按内容指纹准备 Protocol、Extension SDK、已启用本地扩展和 Desktop 发布资产；`pnpm dev` 先执行同一增量预检再启动产品。源码和配置未变化时不会重复全仓 build。通过子包直接启动产品时核对该 product 的 prepare 入口；普通工具/领域测试不要求 Desktop runtime 预检，UI fixture 按相应指南准备当前依赖/Web。

Cognition：

```powershell
cd core/cognition
uv run pytest -q
```

Audio：

```powershell
cd engines/audio
uv run pytest -q
```

UI：

```powershell
pnpm test:ui
```

根 `test:ui` 当前路由到 Desktop；Personal Server 使用其包的 `test:ui` 或 [UI 工具指南](前端开发与UI验收.md) 的定向命令。

## 常见问题

| 症状 | 处理 |
|---|---|
| Vite 端口被占用 | 释放固定端口；开发期不应自动漂移到随机端口 |
| Kernel 未 ready 但 Electron 已显示 | 这是等待态；查看 Kernel readiness 和 process logs |
| Python 包找不到 | 回到仓库根按上方成员/extra 选择执行 `uv sync --inexact`，不要全局 `pip install` |
| 模型下载到用户全局缓存 | 检查 catalog/cache 配置，应落在 `data/models/` |
| Avatar 缺 SDK | 运行 avatar doctor/sync/build，并查看 process log |
| TTS/ASR 不可用 | 先跑 audio `health` 和 warmup，确认资源 catalog |

## 验收

按实际目标判断完成：受控上手取得相应测试/浏览器成果即可；完整 Desktop 开发另确认真实启动的 waiting/ready/degraded、日志与资源退出。
缺 Unity、模型或设备时分别保留相应门，不以受控测试宣称实机可用；密钥不得进入 Git。
