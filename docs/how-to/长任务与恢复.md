# 长任务与恢复

> 适用场景：工作跨上下文、交接、等待外部条件或已有持久任务状态；普通局部任务无需额外账本。
> 事实依据：Git 工作树、任务实际授权、工具句柄；架构 v2 另有机器执行状态和专门任务书。
> 维护触发：任务状态、协作工具、接手或副作用恢复方式变化。

## 保存足够恢复的状态

沿用当前工作已有的状态机制。架构 v2 使用 [execution.json](../roadmap/initiatives/architecture-v2/execution.json)，
操作见 [项目入口](../roadmap/initiatives/architecture-v2/README.md)，不建立第二份迁移进度。
其他长任务在任务允许的位置保留一处记录：

- 用户成果、授权/禁止项、完成和停止条件；
- 唯一写入 owner、工作树/候选、需保留的已有改动、运行命令与等待句柄；
- 已核验事实的路径、决定与理由、待区分假设；
- 实际产物、验证输入/结果/限制、下一项可执行动作和未验门。

稳定知识同步所属文档，运行轨迹和临时进度留在任务记录。简单改动可用短段落，无需复制空模板。

## 恢复与交接

先核对用户目标及后续纠正，再检查实际 Git、owner 和必要进程状态；回读下一步依赖的原文。
输入未变时续用已有证据，动态事实已变时更新判断。不要从历史“下一步”接走其他工作。

分工依据授权、依赖和独立判断价值；委派时明确最小输入、允许动作、资源边界、产物与停止条件。
同一工作树写入在原 owner 停止后才能交接，独立审查者不改候选，整合者检查最终组合。
子智能体、后台命令和用户会话分别管理，不因上下文压缩自动创建或切换用户会话。

## 等待、未知结果与失败

等待使用工具句柄/事件和有界等待。超时、ACK 丢失或远端结果未知，先查询真实 owner/receipt，
再判断重试；发送、部署、付款、发布与数据切换不能盲目重复。连续两次同类无效策略后改变假设或实验。

工具已退出不说明它启动的所有资源都已释放；按本任务拥有的进程、连接和临时根核验收尾，
不要用宽泛 kill、Git reset/clean 或数据清理代替恢复。无法确认副作用时保留原身份、证据与待对账状态。

## 接受与结束

完成、被中断或用户要求停止时，保护已有改动，收束自己持有的临时资源，说明残留任务、未验门和恢复入口。
证据绑定、独立审查与接受标准见 [测试与验收](测试与验收.md)。
