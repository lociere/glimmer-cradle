# 测试与验收

> 范围：项目验证命令、风险到场景的选择和交付标准；agent 证据复用规则由项目 Skill 的《测试与交付》拥有。
> 事实依据：根及各 package 的 scripts、对应测试、CI 与专项指南。
> 维护触发：命令、测试覆盖、验收边界或证据策略变化。
> 适用场景：为改动选择检查并解释结果；前置条件：明确受影响 owner、行为、契约和数据风险。

## 验证范围与命令

开发中先运行能定位问题的定向测试，输入稳定后运行交付门。下表列出各类任务的验证入口，执行时按改动范围选择。

| 场景 | 验证入口 |
|---|---|
| 源码、依赖或构建配置交付 | 根 `pnpm typecheck`、`pnpm build`，加受影响 package 测试 |
| 架构/目录边界变化 | `pnpm check:architecture` 与旧 owner/consumer 搜索 |
| 文本批量改写 | `pnpm check:encoding`、`git diff --check` |
| 纯文档或 agent 指令 | 事实与规则一致性、相对链接、编码、路由和场景推演；Skill 元数据另做格式检查 |
| 全仓回归、共享影响不明或既定 CI 要求 | `pnpm test`，并补不在根测试内的对应场景 |

根测试覆盖架构适配度、Cognition、Audio 与 Kernel 等。UI、Avatar、打包和外部 provider 的实机行为应追加对应验证。纯文档采用文档专项检查；实际 CI、PR 和具体 milestone 的额外要求继续适用。

## 风险到场景

| 改动 | 需要证明的行为 |
|---|---|
| Contract Spine/Schema | `pnpm contracts:generate` / `pnpm contracts:verify`；合法/非法 payload、旧字段与跨语言消费端 |
| Kernel 生命周期 | 启动、ready/degraded/failed、restart/stop、子进程与句柄回收 |
| Cognition | 在 `core/cognition` 执行 `uv run pytest -q`；provider 错误和 outbound |
| Audio Engine | 在 `engines/audio` 执行 `uv run pytest -q`；health、warmup、合成/识别、timeout |
| Web/Renderer | 真实产品入口、受影响状态、路由、键盘/焦点/a11y、视口与必要截图 |
| Desktop/Avatar | Electron/preload/窗口；Avatar doctor/build 与 Unity/Native/打包实机 |
| 权限/会话/异步资源 | 拒权、过期、取消、迟到回调、快速重登、真实 WS/SSE/timer 归属 |
| Extension/Skill Plane | 注册、拒权、确认缺失、调用失败、断连和 dispose |
| 数据迁移 | 备份、旧样本、坏样本、重复迁移、恢复与旧路径退出 |
| 可观测性 | trace、日志、metrics、DLQ、错误定位和脱敏 |
| 打包/部署 | 安装投影、路径、ready/degraded、退出回收和恢复路径 |

helper 测试验证局部逻辑，真实 Host 测试验证请求顺序和权限；组件与产品分别提供对应层级证据，截图与交互检查分别验证视觉和行为。运行前确认测试 fixture 使用当前构建，视觉变化先人工判断再决定是否更新 baseline。

## 执行与失败恢复

Vite/Vitest 配置统一使用 `.mts` 显式 ESM 入口；当前分别位于 Desktop、Personal Server 与 Kernel。新增调用 Vite Node API 的脚本使用 ESM import，CommonJS 脚本使用动态 `import()`。出现 CJS Node API 弃用警告时，在原触发命令中临时设置 `VITE_CJS_TRACE=true` 定位调用者，修复后重跑该入口；不设置 `VITE_CJS_IGNORE_WARNING` 隐藏警告。构建和测试验收同时检查此类警告，不能仅依据退出码判断迁移完成。

1. 明确预期结果和可暴露错误的反例。
2. 确认输入、依赖、构建与环境一致，运行对应门。
3. 失败先区分产品、测试、旧构建、环境或需求理解问题；依据相关错误确定下一项检查。
4. 修正根因后重跑受影响门；共享输入变化时补对应消费面。
5. 稳定后检查最终 diff 和必要交付门，再报告覆盖与缺口。

测试断言、错误处理、fallback 和 ready 判定应保持既定语义。测试本身存在缺陷时，修正并说明覆盖有效性；缺少环境时，记录缺失条件、可复现命令、替代证据和剩余风险。验证结论应注明实际使用的环境。

## 验收与交付

交付说明实际成果、影响边界、验证结果、未运行原因及剩余风险；涉及实机、生产、用户数据时明确所验证环境。简单任务可合成短段落，不强制填写空模板。

源码编译正确、测试通过、独立审查接受、提交、整合、部署是不同状态。高风险改动需要固定候选上的独立判断；未通过必要门只能标记待验。既有成功证据可在输入与相关环境未失效时复用；历史证据不充分时，补充查证后确定当前状态。

工作流设计和评估依据见 [智能体工作流设计](./智能体工作流设计.md)。修改命令、风险场景或接受规则时，同步实际测试入口与 [验证操作卡](../../../.codex/skills/glimmer-cradle/references/workflow/测试与交付.md)。
