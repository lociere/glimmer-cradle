# 前端开发与 UI 验收

> 适用场景：新增或重构 Web、Electron Renderer、Control Center、Presence 的页面、布局、组件、视觉语言、响应式行为与前端测试。
> 前置条件：已阅读根目录 `AGENTS.md`、[开发手册](../开发手册.md)、对应 Product Composition/Implementation，以及 [UI Design Tokens Reference](../../reference/ui-design-tokens.md)；已确认页面 owner、数据 owner、授权范围与用户可观察目标。
> 事实依据：`products/desktop/src/renderer/`、`products/personal-server/src/web/`、Protocol Schema、Product Composition、当前 UI 测试与 W3C/WAI、web.dev 的可访问性和响应式方法。
> 维护触发：前端目录 owner、路由、跨边界投影、设计 token、状态模型、响应式策略、可访问性基线或 UI 验收矩阵变化。

本指南规定可执行流程，不固定某一种审美。重大 UI 改造必须先完成多方向视觉探索并由用户确认，再固化当前 token 与组件语言；历史偏好和既有实现只能作为待比较证据，不能自动成为新方向基线。

使用 Codex、参考图、浏览器截图、Storybook/MCP、社区前端 Skill 或组件库推进 UI 时，同时遵循 [AI 辅助前端开发](./AI辅助前端开发.md)。AI 工作流只增强组件发现、渲染反馈和验证，不改变本页的信息架构、用户确认与验收门。

## 1. 边界与 owner

| 表面 | 负责 | 不负责 |
|---|---|---|
| Personal Server Web | 浏览器路由、Shell、远程管理 feature、共享 API client 与受控投影展示 | 读取服务器文件、YAML、Secret、日志文件、Kernel 内部对象或 Node-only API |
| Electron Renderer | Desktop Control Center、窗口内交互、preload 白名单消费 | 直接读取本机配置、SQLite、Extension 目录、Unity 工程或 Kernel 内部对象 |
| Control Center | 长期管理、对话、配置、能力、日志与受控诊断 | Presence 的轻量常驻交互或 Avatar 渲染生命周期 |
| Presence | 轻量状态、即时交互与受控 Avatar/窗口投影 | 复制完整 Control Center、配置中心或诊断工作台 |

页面和数据 owner 必须分开声明：

- 路由 owner 决定 URL、history、deep-link、页面挂载与离开语义。
- 页面 owner 负责编排 feature，不复制 feature 的业务状态机。
- feature owner 持有本领域 view model、表单、异步状态和局部样式。
- `shared UI` 只持有无领域事实的组件、可访问交互原语与通用布局能力。
- token owner 只表达跨表面的设计语义；feature 不以任意值建立第二套设计系统。
- 系统事实由 Kernel/Protocol/公开 Port 的投影 owner 提供。Renderer/Web 只展示、提交用户 intent，不根据请求时序、DOM、颜色或缓存推断真实状态。

出现新的跨进程字段、命令、错误码或状态组合时，先判断是否需要 Schema/公开 Port。只改变现有投影的呈现方式时，不新增协议；需要前端自行拼接多个内部事实才能判断业务状态时，通常说明投影边界缺失，应停止 UI 补猜并回到 owner 设计。

## 2. 正确实施顺序

1. **固定用户任务**：写清用户要完成什么、成功/失败/降级如何被观察，不从组件或配色开始。
2. **核对事实源**：读取对应 Product Composition、Implementation、Schema/Port、页面入口和既有测试；列出当前事实与目标差距。
3. **建立信息架构**：确定一级域、必要的二级域、对象详情层、全局操作与页面内容容量；删除重复导航和重复位置表达。
4. **固定状态模型**：为页面和关键操作列出 `loading`、`empty`、`degraded`、`error`、`pending`、`success`，以及认证失效、断线、重试与脏状态。
5. **重大改造先做视觉探索**：保持信息架构、内容和功能边界相同，比较至少三个真正不同的方向，等待用户选择或明确混合方案。
6. **确认设计系统**：把用户确认后的当前 token、组件语言和变更规则写入 Reference；未确认变量不得伪装成架构不变量。
7. **按 owner 实现**：先路由与 Shell，再共享原语，再 feature 与页面；同步删除被替代的旧入口、旧样式和兼容壳。
8. **逐级验证**：静态/单元检查、组件与路由交互、截图矩阵、真实浏览器或 Electron 实机；失败时先修最小根因。
9. **同步文档**：当前实现进入 Implementation/Reference，操作进入 Guide，未完成优化进入 Roadmap。

AI 辅助任务在第 2–8 步之间使用短反馈环：先观察当前页面与组件 API，再实现一个内聚片段，立即在真实浏览器渲染并查看截图，随后运行最相关的交互、可访问性和响应式检查。不能在没有看过实际渲染结果时把“代码已生成”当成 UI 完成。

## 3. 信息架构与路由

每个一级入口必须对应一个稳定用户任务域，不以技术模块数量、后端 service 或“有一张卡片可放”为理由增加导航。二级导航只在当前域内存在真实子域时出现；当前位置只由一个主标题和必要 breadcrumb 表达，避免顶栏、侧栏、页面标题重复同一句话。

对象详情使用列表/主体 + 按需详情层。Context Drawer 只有在用户选中 runtime、日志、Extension、Provider 等真实对象时才出现；未选中对象时不得常驻空洞 Inspector 挤压工作区。

浏览器正式页面的路由至少覆盖：

- 可分享或可恢复的 URL；
- history 与 back/forward；
- 刷新和 deep-link；
- 未知路由与权限拒绝；
- 页面进入、离开、焦点恢复和未保存更改；
- 当前页面唯一可见；非当前复杂页面不应继续参与布局或无理由常驻执行；
- 离开页面时完成 stream、listener、timer、observer、临时请求和上传资源的 lifecycle cleanup。

原生 `hidden`、`inert`、`aria-hidden` 和 CSS 显示规则必须语义一致。不得让通用 `display` 规则覆盖 `[hidden]`；登录遮罩出现时，不应同时向可访问树或布局暴露未认证应用壳。

## 4. 视觉探索与设计系统

重大 UI 改造编码前执行以下门禁：

1. 固定相同的信息架构、代表任务、内容、状态和功能边界。
2. 先用同一代表任务比较至少三个真正不同的视觉方向；差异不能只是换颜色。
3. 候选比较至少覆盖宽屏与窄屏，足以判断结构、容量和响应式策略。
4. 用户选择方向或明确混合元素后，为最终方向补齐对话、系统概览、设置，以及深色、浅色、宽屏、窄屏和关键状态矩阵。
5. 比较字体与比例、色彩、表面、品牌表达、导航、信息密度、动效、可访问性和长期维护成本。
6. 允许学习成熟产品、官方设计系统与先进 frontend Skill 的方法，但只吸收思考方法，不复制品牌、布局、颜色、图标、代码、模板或 token。
7. 选择前不得替用户固化最终视觉语言；用户确认后，才把具体 token 与组件语言写入 [UI Design Tokens Reference](../../reference/ui-design-tokens.md) 并进入实现。

框架、组件工作台和 UI 库属于工程决策，不是视觉方向本身。框架迁移必须通过 ADR/目标物理清单说明收益、代价、迁移顺序和旧入口删除门；不得仅因某个 AI Skill、MCP 或热门组件库更易生成代码而改变架构。

评价方向时回答：

- 是否真正好看、协调、完整且具有设计意图；
- 是否适合个人长期使用，而不是营销演示或临时后台；
- 是否与 Glimmer Cradle 产品身份协调；
- 是否具有清晰层级、良好比例和一致的信息密度；
- 是否避免通用 AI 模板感；
- 是否兼顾可用性、响应式、可访问性和维护成本；
- 是否能收敛成有限、可复用的 token 与组件系统。

不得预设必须深色或浅色、克制极简、系统字体，或必须使用某一种表面、渐变、阴影、透明、纹理。Guide 不保存具体 token 数值；精确当前值与待选择变量在 Reference 维护，前端框架边界以 ADR-0017 为准。

## 5. 状态、容量与响应式

### 状态完整性

所有数据区和异步操作至少检查：

| 状态 | 最低要求 |
|---|---|
| `loading` | 保留布局意图，说明正在取得什么；避免把永久空白当加载 |
| `empty` | 说明为何为空、是否正常、下一可行动作 |
| `degraded` | 展示仍可用能力、受限原因和恢复入口，不伪装 ready |
| `error` | 可理解错误、重试/返回路径、必要 trace 或诊断入口 |
| `pending` | 防重复提交、保留用户输入、明确取消或等待语义 |
| `success` | 反馈已完成内容、当前 effective 状态及 reload/restart 要求 |

列表还要覆盖零项、单项、大量项、长名称、未知枚举和部分失败；表单覆盖初始值、脏状态、校验、并发 revision 冲突、保存失败、重置和 Secret write-only。日志默认错误与告警优先，详情按需展开，不把大量 debug 卡片当首页。

### 内容容量

响应式以内容最低容量为依据，不以“桌面/平板/手机”标签或任意百分比决定：

- 为每种页面声明主要任务区的最低可用宽度、理想阅读宽度和最大有效宽度。
- 表单、对话、日志、表格和详情页可拥有不同内容宽度，不强制同一 `max-width`。
- 从窄布局开始扩展；当内容、控件或可读行长需要变化时才设置断点。
- 侧栏、Drawer、Overlay 与主区竞争空间时，优先保证主要任务；隐藏的是重复 chrome，不是用户需要的内容或功能。
- 验证长中文/英文、技术 ID、错误堆栈、100–400% 缩放、触屏与无 hover 环境。
- 组件需要根据局部容量变化时优先评估容器约束，不把所有决策绑到全局 viewport。

## 6. 可访问性

以 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 的 AA 成功标准作为最低验收基线，并参考 [WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/) 的交互模式；APG 是交互方法，不是视觉设计系统。

- 优先使用语义 HTML；只有原生语义不足时才添加 ARIA，名称、角色、值和状态必须同步。
- 所有功能可用键盘完成，DOM/阅读顺序与视觉顺序一致；Overlay 打开、关闭和返回时管理焦点。
- `focus-visible` 清晰、连续、不被 sticky/overlay 遮挡；颜色不是唯一反馈。
- 浏览器缩放、文本放大和 320 CSS px 等效宽度下不得丢失信息或要求双向滚动，确需二维布局的内容除外。
- 不禁止缩放；正文和控件文字响应用户字号偏好，避免只依赖 viewport 单位。
- 动效服从 `prefers-reduced-motion` 或产品等价偏好；移除非必要运动后仍保留状态变化含义。
- 触控目标达到 WCAG 2.2 的最低目标尺寸或满足允许例外，并保持足够间距；拖动必须有非拖动替代。
- 图标按钮提供可访问名称；陌生图标有文字说明或 tooltip；品牌资产不代替控件标签。
- 标题层级、landmark、表单 label、错误关联、live region 和语言属性保持正确。

## 7. 验证矩阵

先根据风险选择矩阵，不用单张“看起来正常”的宽屏截图代替验收。

### 代表页面与状态

- 代表页：对话、系统概览、设置；涉及列表/详情时再加入日志、runtime、Extension 或 Provider。
- 每页至少覆盖默认、loading、empty、degraded、error；有写操作时再覆盖 pending/success、脏状态与冲突。
- 认证表面覆盖未登录、登录失败、登录中、会话过期、重新登录；未认证时应用壳不参与可访问交互。

### 视口与输入

- 宽屏、临界容量、窄屏，以及断点前后各一个尺寸；尺寸由当前页面容量推导并记录。
- 100%、200%、400% 缩放；长内容和大数据量。
- 鼠标、键盘、触控/粗指针；reduced-motion；必要时深浅或高对比主题。
- Desktop 额外覆盖 Electron 窗口最小尺寸、DPI、窗口按钮、preload 白名单与实机焦点。

### 自动化断言

- 路由 URL、刷新、deep-link、back/forward 与未知路由；
- 目标页面可见，所有非当前页面不参与布局或可访问交互；
- Overlay/Drawer 的打开、`Escape`、遮罩关闭、焦点进入与返回；
- 关键状态文本、语义、禁止重复提交和失败恢复；
- 无横向溢出、主要任务区不低于容量阈值；
- 代表页面与关键状态的稳定截图基线；动态时间、随机 ID 和敏感信息先做受控归一化。

截图用于发现层级、比例、换行、密度和视觉回归，不能替代真实点击、输入、滚动、键盘、焦点与网络失败测试。实现完成后按受影响范围运行包级 typecheck/build、Playwright 与浏览器或 Electron 实机；若本任务不改运行时，则只运行文档与 Skill 门禁并明确说明。

## 8. 失败与恢复

- 信息架构或视觉方向未确认：停止实现，保留同内容多方向材料，向用户请求最小选择。
- 需要前端推断系统事实：停止补 UI 条件，回到 Schema/Port 与投影 owner。
- CSS 修复导致旧结构仍在布局或可访问树：删除被替代入口，不以更高 specificity 或永久兼容选择器掩盖。
- 截图在不同机器漂移：先固定字体来源、动画、时间、数据和 viewport；不得放宽到无意义阈值。
- 临界宽度失败：记录实际内容容量，调整布局规则和断点依据；不要继续叠加设备特例。
- 可访问性与视觉方向冲突：可用性为门禁，调整方向或 token，不以“更好看”为理由降级键盘、对比、缩放或语义。

## 9. 文档同步与交付

- 页面/装配/数据链路变化：同步对应 Implementation。
- token 当前值、语义 owner 与变更规则：同步 [UI Design Tokens Reference](../../reference/ui-design-tokens.md)。
- Product Host 与浏览器/Electron 边界变化：同步 [Product Compositions](../../reference/product-compositions.md) 或对应 Current。
- 未完成问题、视觉探索门或后续验收：进入 Roadmap，不写成当前事实。
- 长期架构取舍变化：由总控决定是否需要 Blueprint/ADR；执行者不自行升级。

交付说明必须列出：用户任务、改动 owner、当前实现与目标的边界、选定视觉方向及确认来源、状态覆盖、视口/输入/缩放矩阵、已运行验证、未运行验证及原因、旧结构清理、文档同步与剩余风险。
