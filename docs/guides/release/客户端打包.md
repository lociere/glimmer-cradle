# 客户端打包

> 适用场景：构建 Glimmer Cradle 桌面客户端、验证安装投影、检查 Avatar/Audio/native 等组件是否可发布。
> 前置条件：已读 [Packaging Layout Reference](../../reference/packaging-layout.md)，工作树不包含无关本地资产或密钥。

## 步骤

1. 执行 `git status --short`，确认不会把私人模型、secret、缓存或测试输出打入包。
2. 运行基础验证：

```powershell
pnpm typecheck
pnpm build
```

3. 正式 clean workflow 由 Avatar owner job 通过固定摘要的 Unity/Cubism 工具链与许可入口
   构建、attest fixed artifact；Desktop job 只在 commit/digest/attestation 全部通过后消费。
   本地手工 Avatar build 不能替代该可信制品门。
4. 如涉及 Audio，运行 audio 测试和必要的 `health`/warmup，确认模型目录与 resource catalog。
5. 先检查无副作用计划，再构建客户端包：

```powershell
pnpm --filter @glimmer-cradle/desktop package:dry-run
pnpm --filter @glimmer-cradle/desktop package:runtimes:dry-run
pnpm --filter @glimmer-cradle/desktop package
pnpm --filter @glimmer-cradle/desktop verify:package -- `
  dist/desktop/<version>/windows-x64 `
  --expected-commit <full-commit> `
  --expected-manifest-digest <sha256> `
  --expected-builder products/desktop/scripts/package.mjs `
  --expected-issuer github-actions-sigstore
```
6. 用 unpacked/打包产物通过正式 `packaged-paths.ts` 与 `packaged-supervisor.ts` 首启，
   不用开发服务器或 root launch script 结果代替安装态验收。
7. 检查用户数据、日志、模型、缓存是否写入 user-data/data 域，而不是安装目录。

## 发布检查

| 检查 | 要求 |
|---|---|
| Secret | 包内无真实 `configs/secrets/secrets.yaml`、provider key、token；只允许空值 `secrets.example.yaml` 模板 |
| 私有资产 | 包内无私人 Avatar 模型、训练语料、个人声线，除非明确发布资源 |
| required 组件 | bundled Node/Python、Kernel resolved dependencies、安装后的 Contracts/Cognition/Audio、Avatar、Extension Host、native 与 Desktop product manifest 均能定位；隔离 Python 能 import canonical generated module 并启动 Cognition module |
| ready/degraded | 缺资源时能解释 degraded，不伪装 ready |
| Avatar | 打包版验证透明、DPI、多显示器、拖动、动作、口型、退出 |
| Audio | TTS/ASR provider、cache、process log、timeout 可诊断 |
| Logs | 主日志和 process log 写入 `data/observability/` |
| 停机 | 退出能回收 sidecar、stdio、WebSocket 和子进程树 |
| 供应链证据 | installer、完整 unpacked/component manifest、`artifact-manifest.json`、`provenance.json`、组件级 `sbom.spdx.json`、unsigned `build-claim.json` 同目录且 integrity verifier 通过；可信结论还必须通过 GitHub Sigstore attestation |

## 失败与恢复

- 缺 required 构建输入：停止打包，补资源或改为明确 optional。
- 打包版写安装目录：修 resolver，不通过改权限绕过。
- Avatar 只有 `host_hello` 没有 `host_ready`：查 Unity model/SDK/Composition Host 首帧，不把连接当 ready。
- Audio 首次请求才下载模型：把资源准备前移到 warmup/readiness。
- 包内出现 secret 或私人资产：删除包，修打包规则和 ignore，再重新构建。
- 非 Windows 执行正式 package：任务失败闭合；当前只支持 Windows x64，不能从 dry-run
  外推安装、首启、升级或卸载已经通过。
- clean runner 缺 Unity Editor/许可、native toolchain 或任一六类 component projection 时：
  package 失败闭合；不得用空目录、fixture installer 或 unsigned claim 伪装成功。
- bundled runtime、lock export、component manifest、attestation identity 或正式 supervisor
  任一缺失：停止，不得回退到系统 Node/Python 或 root `scripts/launch-product.mjs`。
- 隔离 smoke 只证明安装投影 resolver/supervisor 的 ready/degraded/stop/cleanup 控制流；
  真实 Windows installer 安装、首启、升级、卸载、Unity、签名与公证仍须固定制品实机矩阵。
