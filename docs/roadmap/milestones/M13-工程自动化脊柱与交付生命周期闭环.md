## 目标成果

把 Scripts、Automation、CI、Build、Release、Install 与 Ops 收口为与运行时架构同等完整、可长期自然演化的工程生命周期平面：

```text
source
  -> owner-local atomic task
  -> repository thin orchestration
  -> CI
  -> fixed artifact
  -> install / ops
```

完成后，package/product/host/domain owner 拥有原子任务与领域语义；root 只编排真正跨 owner 的公共任务；workflow 只调用本地也能调用的公共任务；Release 只消费带 manifest、digest 与 provenance/attestation 的 fixed artifact；同一宿主的安装、更新、备份、恢复、回滚和回收由唯一 host-global transaction owner 串行化。

本里程碑只承诺未来实现与验证，不表示当前 Scripts、CI、Build、Release、Install、Ops 或 Desktop packaging 已经达到目标。每个切片完成后，当前事实才进入 Current、Implementation、Reference 与 Guide。

## 范围

- 部署与安装事务的宿主级锁、稳定 handoff、自替换安全、幂等、回滚和结构化诊断。
- 备份 retention 分域、Smoke 真隔离、DLQ replay/resolve/cleanup 语义与默认脱敏。
- owner-local task graph、root 薄编排、local/CI parity、PR CI、Windows/Linux 基础门、encoding 完整 inventory 和 prepare output manifest。
- Avatar、Personal Server、Data tooling 等任务实现归还 owner，root 只保留薄 wrapper；旧入口按消费者归零删除。
- 固定 base image、最小权限、tar/OCI/installer provenance 与可独立验证 attestation。
- Desktop packaging 作为独立产品矩阵，拥有自己的 package/release 入口、fixed artifact、支持平台和验收门，不与 Personal Server Release 耦合。
- 为所有公共任务补齐 inputs、outputs、side effects、lock、idempotency、confirm、dry-run、exit code、log/diagnostic 和 cleanup/recovery contract。
- 实现切片落地时同步唯一 Current、Implementation、Reference 与 Guide 事实源。

## 非范围

- 不改变 Cognition、Kernel、Avatar、Engine、Extension、Contracts 或产品 Surface 的领域主权。
- 不修改 M12 Contract Spine 的 baseline、Service 语义、迁移切片或验收门；M12 后续若修改相同 build/package 入口，必须以 fixed-state handoff 串行化。
- 不以工程重排为名重写产品功能、运行时协议、人格、记忆、Avatar 行为或 Provider 算法。
- 不把 Nx、Turborepo、Taskfile 或任何特定工具作为验收成果；工具可替换，架构契约不可漂移。
- 不建设托管云 CI、私有 Registry、通用制品平台或多租户运维控制面。
- 不把 Desktop 产品矩阵混入 Personal Server Release，也不把 Personal Server 当前成功发布证据当作 Desktop 已可打包。
- 不长期保留新旧 task、prehook、wrapper、workflow 或 deploy/ops 主线。
- 不提前把本 milestone 的目标写入 Current、Implementation、Reference 或 Guide 作为已实现事实。

## 进入门与依赖

M13 的首个实现切片只能在以下条件同时满足后由总控显式切换为 `in-progress`：

1. M12 当前 Slice 1 已形成并集成 fixed-state commit，相关 writer 已释放；
2. 总控明确把当前唯一活跃推进面从 M12 Slice 1 切换到 M13 的一个指定切片；
3. 该切片的 source、task、workflow、artifact、install/ops consumer inventory 已冻结；
4. 与 M12 后续切片、M11、Release 或生产环境不存在同一文件/工作树/宿主的 active writer 冲突；
5. 输入 commit、工具链锁定状态、支持平台和可复用验证账本已经记录。

该进入门不关闭、扩大或重定义 M12；如果 M12 后续切片需要修改同一 build/generate/package 入口，两个里程碑只能按固定 commit 串行交接，不能并行写入。

实现依赖包括：

- ADR-0015 的 owner、单向链与任务契约；
- 当前 package、product、host、root scripts、workflow、deploy/install/ops、artifact 和文档 consumer inventory；
- Windows/Linux 可用的固定 Node/Python/.NET/Unity/Electron/Docker 工具链与最小权限 runner；
- 可在隔离 fixture、临时宿主或专用测试环境验证 deploy、backup、restore、DLQ 和 self-replacement，不以健康生产服务器作为故障注入场；
- 每个产品 owner 对 fixed artifact、支持平台、安装投影与数据边界的明确签字。

## 任务契约与单向链

所有实现切片必须让公共任务以机器可验证方式声明：

| 字段 | 验收要求 |
|---|---|
| `inputs` | fixed source、配置、依赖、平台、凭据引用和前置 artifact 完整可枚举 |
| `outputs` | 文件、目录、manifest、digest、报告或明确无持久输出；prepare 任务不得只产 sentinel |
| `side effects` | 文件、权限、网络、token、进程、容器、数据库、服务与宿主状态变化完整可审计 |
| `lock` | owner-local、repository 或 host-global 锁及争用 exit code；状态查询不得无故获取写锁 |
| `idempotency` | 重复执行结果、幂等键或明确非幂等边界 |
| `confirm` | 高风险动作需要显式确认；非交互环境缺确认时拒绝 |
| `dry-run` | 输出计划与诊断但不创建长期 token/env/state 或其他业务副作用 |
| `exit code` | 稳定区分成功、验证失败、前置缺失、锁冲突、用户拒绝、部分提交和恢复失败 |
| `log/diagnostic` | 结构化阶段、owner、trace/correlation、脱敏摘要、artifact/digest 和恢复入口 |
| `cleanup/recovery contract` | 成功、失败、取消、崩溃时的资源回收、补偿、回滚或人工恢复终态 |

所有切片都遵守：

- package-local task 先独立通过，root 再薄编排；
- 本地与 CI 调用同一公共任务；
- CI 只保存证据，不复制任务逻辑；
- Release 只消费前序 CI 固定的 artifact；
- Install/Ops 只消费 fixed artifact 并由 host-global transaction owner 串行化；
- 新链通过后删除旧入口，不能把兼容 wrapper 留作永久第二主线。

## 实施切片

六个切片分别形成 clean fixed state。具体执行顺序由进入时的依赖图决定，但同一文件、workflow、artifact 或宿主只有一个 writer；A/B/E 涉及宿主与发布环境时必须在隔离测试环境先过门，不能直接以生产操作作为首次验证。

### Slice A：部署事务安全

- **Owner**：Install/Ops transaction owner；Ops Bridge owner 只拥有 handoff Adapter，不拥有宿主事务。
- **输入 fixed state**：目标 source commit、现有 deploy/install/ops/bridge consumer inventory、同名进程/容器/服务关系、备份与回滚入口、隔离宿主 fixture 已冻结。
- **输出 fixed state**：所有安装、更新、重启、回滚和卸载入口共享 host-global lock；Ops Bridge 在被替换前把事务交给稳定外部 owner；self-replacement 集成矩阵与结构化事务日志通过。
- **允许修改**：未来实现切片中的 owner-local deploy/install/ops core、thin shell wrapper、Ops Bridge handoff Adapter、隔离集成 fixture、对应 workflow 和事实文档。
- **非范围**：不修改运行时业务协议，不操作未授权生产宿主，不让 Kernel 或 Extension 接管宿主部署事务。
- **删除门**：所有旧 deploy/install/restart/update 入口都改为调用唯一事务 owner；搜索和集成测试证明没有绕锁入口、bridge 自删链或旧并行状态机后，删除旧锁、旧 self-restart 路径和兼容 wrapper。
- **主要风险**：锁粒度过大造成查询阻塞；进程 handoff 丢失事务；崩溃后锁泄露；回滚与新事务竞态；status/logs 查询仍提前创建 token/env/state 或权限。
- **分层验证**：
  1. task contract 静态校验：lock、side effects、dry-run、exit code 与 recovery 字段完整；
  2. 原子测试：锁争用、幂等重入、stale lock 归属校验、确认拒绝、只读 status/logs 无持久副作用；
  3. 隔离集成：Ops Bridge 发起 update/restart 后由外部 owner 完成 handoff，旧 bridge 被回收但事务不中断；
  4. 故障注入：prepare、replace、restart、readiness、commit 各阶段崩溃均能回滚或进入可查询人工恢复态；
  5. Windows/Linux wrapper 与 exit code/diagnostic 一致性。
- **完成后事实迁移**：事务 owner、锁与进程关系进入 Current；代码入口和 handoff 状态机进入 Implementation；任务字段、exit code、日志和锁语义进入 Reference；部署、回滚、锁冲突与恢复步骤进入 Guide。

### Slice B：数据与恢复安全

- **Owner**：Data/Recovery owner；DLQ owner 负责失败证据生命周期，Smoke fixture owner 负责隔离投影。
- **输入 fixed state**：manual、transaction、restore-safety backup 的生产者/消费者/retention inventory，Smoke data/models/packages 访问图，DLQ replay/show/resolve/cleanup 状态机与样本已冻结。
- **输出 fixed state**：三类备份独立 retention；Smoke 只访问隔离副本且不能经可写 link 进入真实数据域；DLQ replay 真正重投 payload，resolve 与 cleanup 分离，默认输出脱敏。
- **允许修改**：未来 owner-local backup/restore、Smoke fixture、DLQ tooling core、thin wrapper、测试样本与对应事实文档。
- **非范围**：不改变 Cognition/Kernel 的领域数据模型，不批量清理现有真实备份或 DLQ，不以文档重命名代替状态机迁移。
- **删除门**：旧混合 cleanup、可写真实数据 link、仅标记 `replayed` 的伪重放、resolve 即删除和默认 raw show 入口全部无 consumer；迁移/保留策略验证后删除。
- **主要风险**：误删手工或恢复安全备份；Smoke 污染真实 state/models/packages；重复重放产生副作用；未恢复证据被 resolve/cleanup 删除；raw payload/stack 泄露隐私或密钥。
- **分层验证**：
  1. retention 属性测试覆盖 manual、transaction、restore-safety 的独立保留与清理边界；
  2. Smoke 在临时根运行，禁止写入真实 `data/`，校验 inode/path/link/ACL/容器挂载与退出后清理；
  3. DLQ replay 以真实 handler/queue receipt、correlation 和终态证明 payload 被重新提交；失败保持可重试证据；
  4. resolve 需要显式原因与审计，cleanup 只处理满足 retention 和终态的记录；
  5. `show` 默认只给脱敏摘要；raw payload/stack 需要显式高权限、确认与审计；
  6. 备份恢复、重复执行、取消和崩溃恢复集成矩阵。
- **完成后事实迁移**：数据域与状态机进入 Current；backup/Smoke/DLQ 入口和链路进入 Implementation；retention、字段、权限、脱敏和 exit code 进入 Reference；备份恢复、DLQ 操作和失败恢复进入 Guide。

### Slice C：Task graph 与 CI parity

- **Owner**：Repository automation owner 负责跨 owner 图；各 package/product/host owner 负责自己的原子任务；CI owner 只负责 runner 与证据。
- **输入 fixed state**：root/package scripts、pre/post hooks、workflow、workspace、encoding、ignore、deploy、contracts、prepare outputs 和平台 shell inventory 已冻结。
- **输出 fixed state**：公共 task graph 无重复 prehook；PR CI 调用与本地相同的公共任务；Windows/Linux 基础门存在；encoding inventory 完整；prepare 产生 output manifest/digest。
- **允许修改**：未来 owner-local task 定义、root thin orchestration、PR/tag workflow、跨平台 core/thin wrapper、encoding inventory、prepare manifest 与测试。
- **非范围**：不切换 task runner 作为目标，不重写产品逻辑，不在 workflow 内新增本地不可调用的业务任务。
- **删除门**：重复 protocol/contracts build prehook、workflow 私有实现、隐含 Bash 的公共 Windows 入口、漏检 inventory 和 sentinel-only 成功路径都有替代公共任务并通过矩阵；随后删除旧 hook/step/wrapper/sentinel 判定。
- **主要风险**：去重后遗漏依赖；cache 命中错误输出；Windows wrapper 与 Linux core 语义分叉；PR 门与 Release 门仍消费不同任务；encoding 漏 `contracts/`、`deploy/`、`pnpm-workspace.yaml` 或 ignore 文件；prepare manifest 与实际输出漂移。
- **分层验证**：
  1. task graph 静态快照证明每个原子任务唯一 owner、依赖无环、同一 protocol/contracts build 不被 root 与 package hook 重复触发；
  2. package-local task 独立运行后，root 只聚合调用与 exit status；
  3. PR CI 在 clean Windows/Linux runner 调用公共 check/typecheck/test/build 中的风险匹配子集，tag Release 复用相同基础门；
  4. Windows onboarding 的公共 `pnpm test` 不隐含 Bash；thin wrapper 合同测试覆盖路径、signal 与 exit code；
  5. encoding inventory 覆盖所有受管 `.ts/.tsx/.py/.yaml/.json/.md` 及 `contracts/`、`deploy/`、workspace/ignore 配置；
  6. prepare output manifest 枚举文件、size、digest、toolchain 与 source commit，篡改/缺失/sentinel 残留均失败；
  7. local/CI 命令、输入、输出和诊断快照对比。
- **完成后事实迁移**：task graph 与 CI 拓扑进入 Current；任务入口、依赖解析和 manifest 生成进入 Implementation；公共命令、manifest、exit code 与平台矩阵进入 Reference；本地/CI 开发步骤和失败恢复进入 Guide。

### Slice D：Owner-local 物理收口

- **Owner**：Avatar、Personal Server、Data tooling 等领域 owner 分别拥有实现；Repository automation owner 只拥有 root wrapper 与跨 owner 编排。
- **输入 fixed state**：root `scripts/` 中每个任务的领域语义、真实 consumer、package/product/host owner、workflow/guide 调用者和旧入口清单已冻结。
- **输出 fixed state**：Avatar、Personal Server、Data tooling 的原子任务物理归所属 owner；root 只保留稳定薄 wrapper；task graph、workflow、文档和调用者全部指向 owner-local 主线。
- **允许修改**：未来对应 owner 目录内的 automation core/atomic tasks、root thin wrapper、调用者、task graph、测试与事实文档。
- **非范围**：不借机移动领域源码，不重排 M12 的 `contracts/` baseline，不把公共 SDK 或跨产品包准入规则改写成脚本归属规则。
- **删除门**：owner-local task 通过本地/CI/产品矩阵，所有 consumer 切换且旧 root 实现搜索归零；删除重复逻辑、兼容 re-export 和无期限 wrapper，只保留确有跨仓价值的薄入口。
- **主要风险**：机械移动文件但保留 root 业务状态机；owner-local 任务依赖 root 私有 helper；多个产品共享假象导致 owner 不清；旧 Guide/workflow 继续调用旧入口。
- **分层验证**：
  1. owner inventory 对每个任务给出唯一 package/product/host/data owner；
  2. import/call graph 证明领域逻辑位于 owner，root wrapper 只转发参数和结果；
  3. owner-local task 可脱离 root 私有实现独立测试；
  4. root orchestration 只覆盖真实跨 owner 图，并在 Windows/Linux 保持相同语义；
  5. 旧入口、旧路径、重复 helper 与 workflow/Guide 引用归零。
- **完成后事实迁移**：物理 owner 与 root 职责进入 Current；真实 task/composition 入口进入 Implementation；命令与 owner 查表进入 Reference；开发、打包和数据工具操作进入对应 Guide。

### Slice E：可复现供应链

- **Owner**：Release/Supply-chain owner；各产品 owner 对自己的 artifact manifest 与可安装性负责。
- **输入 fixed state**：base image、builder、依赖、tar/OCI/installer 产物、checksum、Registry、Release workflow、权限和来源证据 inventory 已冻结。
- **输出 fixed state**：base image 以 digest 固定；CI/Release 使用最小权限；tar、OCI 与后续 installer 均带可独立验证的 manifest、provenance/attestation 和 source/toolchain/artifact 绑定。
- **允许修改**：未来 image/build definitions、artifact manifest/attestation 生成与验证、Release workflow、权限、供应链测试和事实文档。
- **非范围**：不自建通用 CA、Registry 或托管签名平台；不以变更供应链为名重写应用内容；不把 Desktop 与 Personal Server 合并成一个制品。
- **删除门**：tag-only base image、只有 checksum 的 tar 证明、过宽 workflow permission、Release 现场重构建和无法追溯 source 的 artifact 均有替代并通过独立验证；随后删除旧未固定入口和冗余证明。
- **主要风险**：digest 与可更新性冲突；attestation 由同一不可信步骤自证；权限缩小后上传/签名失败；tar 与 OCI provenance 语义不一致；离线安装无法携带验证材料。
- **分层验证**：
  1. base image 与 builder digest/版本/来源锁定检查；
  2. 同一 fixed source 在 clean runner 重建并比较规范化 manifest/digest；
  3. tar 与 OCI 分别验证 checksum、manifest、source commit、builder identity、dependency/base digest 和 provenance/attestation；
  4. verifier 独立于 producer 运行，篡改 artifact、manifest、attestation 或 source binding 均失败；
  5. workflow permission 负向测试证明 PR、Release、artifact read/write 各阶段仅获所需权限；
  6. remote/full/offline 安装消费已验证 fixed artifact，不回源或现场重构建。
- **完成后事实迁移**：产品/制品关系进入 Current；生成、签名/证明和消费链进入 Implementation；manifest、digest、provenance、权限与打包映射进入 Reference；发布、验证、离线安装和失败恢复进入 Guide。

### Slice F：Desktop packaging 产品矩阵

- **Owner**：Desktop product owner；Avatar/Native/Audio owner 提供固定依赖 artifact，Release owner 只发布 Desktop fixed artifact。
- **输入 fixed state**：现有 Electron builder 配置、Desktop/Avatar/Native/Audio build outputs、资产许可、Windows 支持范围、安装数据投影和 Personal Server Release 边界 inventory 已冻结。
- **输出 fixed state**：Desktop 拥有独立可执行 package/release 公共任务、artifact manifest/digest/provenance、安装/升级/卸载矩阵和产品级验收证据；Personal Server Release 不再被当作 Desktop 交付代理。
- **允许修改**：未来 Desktop owner-local packaging core、thin wrapper、artifact manifest、产品 workflow、安装 fixture、实机测试和事实文档。
- **非范围**：不改变 Desktop UI、Avatar 领域语义或 Personal Server Release；不在未确认资产许可、签名和支持系统前宣称正式发布。
- **删除门**：仅有 builder 配置/Guide 但无可执行 package/release 的空壳入口被真实任务替代；所有 consumer 指向 Desktop 产品主线后删除临时命令、复用 Personal Server 的错误入口和重复产物定义。
- **主要风险**：Electron、Unity、Native DLL、Audio/model 资产版本漂移；签名或许可缺失；安装目录与用户数据混淆；打包成功但首启/readiness/卸载残留失败；错误耦合 Personal Server tag/release。
- **分层验证**：
  1. Desktop package-local task 从 fixed source 和固定 Avatar/Native/Audio outputs 生成 manifest；
  2. Windows clean runner 构建、安装、首启、readiness、升级、失败回滚、卸载和用户数据保留矩阵；
  3. artifact 缺失、digest 篡改、资产许可缺失、Native/Avatar 不兼容时 fail closed；
  4. Desktop workflow 与 Personal Server workflow 的输入、产物、版本和权限边界独立；
  5. 安装包结构、签名/证明、日志、诊断与 recovery contract 可验证；
  6. 未来新增平台必须以独立 fixed-state matrix 晋升，不能从 Windows 结果外推。
- **完成后事实迁移**：Desktop 产品/Host/依赖关系进入 Current；package/release/安装链进入 Implementation；制品、目录、manifest、支持平台和数据投影进入 Reference；Desktop 打包、发布、安装、升级、卸载和排障进入 Guide。

## 里程碑验收门

### 架构与 owner

- 所有公共任务都有唯一 owner；领域原子任务位于 package/product/host/data owner，root 只做跨 owner 薄编排。
- Workflow 只调用公共任务；不存在只在 CI YAML 中成立的业务逻辑。
- 每个任务的十项契约均可机器验证；status/logs/doctor/dry-run 默认无持久业务副作用。
- Install/Ops 对同一宿主只有一个 transaction owner；lock、handoff、幂等、补偿、回滚和人工恢复终态完整。
- 新链通过后，旧 root 实现、重复 prehook、workflow 私有逻辑和兼容 wrapper 已按删除门清理。

### 数据与恢复

- manual、transaction、restore-safety backup 分域，retention 互不越权。
- Smoke 不接触真实 state/models/packages 的可写路径、link 或挂载；失败和取消后无临时残留。
- DLQ replay、resolve、cleanup 是不同动作；真实重放有 receipt/终态，默认展示脱敏，原始数据访问有权限和审计。

### Task graph 与 CI

- 本地、Windows/Linux PR CI、tag Release 复用同一公共任务和稳定 exit code。
- Task graph 无重复 protocol/contracts prehook，依赖、缓存输入和输出 manifest 可解释。
- Encoding inventory 覆盖源码、契约、deploy、workspace 与 ignore 文件；UTF-8 无 BOM 门通过。
- Prepare 任务产生内容完整的 manifest/digest，不以 sentinel 代表成功。

### 制品、供应链与产品

- Release 只消费 CI 已固定 artifact；tar、OCI、Desktop installer 分别有 manifest、digest 与可独立验证 provenance/attestation。
- Base image、builder、关键依赖和工具链由版本与 digest 固定；CI/Release/Install 使用最小权限。
- Personal Server 与 Desktop 是独立产品矩阵；Desktop package/release、安装、首启、readiness、升级、回滚、卸载和数据保留有实机证据。
- Fixed artifact 在 remote/full/offline 或对应产品安装路径中不现场重构建、不隐式回源。

### 验证与文档

- 六个 slice 各自有输入/输出 fixed state、owner、允许修改、非范围、删除门、风险和分层验证账本。
- 先通过 owner-local 静态/单元门，再通过 root/task graph、CI、制品、隔离安装/恢复与产品实机矩阵；前一级失败不升级。
- 所有 Scripts 审查 P1/P2 风险都有失败前证据、修复后验证和旧入口删除证据。
- Current、Implementation、Reference 与 Guide 只在对应实现 slice 落地后同步为当前事实；Blueprint、ADR-0015 与本 milestone 继续分别保存长期不变量、取舍和未完成承诺。
- 没有后台测试、临时宿主、容器、挂载、锁、token、备份 fixture 或未清理 artifact。
