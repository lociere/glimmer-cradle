## 1. 产品任务与体验目标

Personal Server 是长期运行的个人控制面，不是营销站、通用 SaaS Dashboard 或 Desktop 的远程镜像。用户进入后应能快速回答：

1. 当前是否健康；若降级，仍可用什么、为什么、如何恢复；
2. 当前对话是否可继续，Provider/Audio/Memory 等能力处于什么状态；
3. 哪个 runtime、Extension、日志或设置对象需要处理；
4. 保存、重启、更新、安装或高风险操作产生了什么实际结果。

目标体验是安静、可信、可长时间使用，同时在需要诊断时具有足够信息密度。深色主题由中性黑/炭黑/灰构成，浅色主题由白/近白/中性灰构成；两者都不被强调色色相染色。品牌感来自清澈层次、含蓄光感、比例和交互细节；青曜只用于少量交互强调，状态色保持独立，不依赖装饰性卡片墙或全页特效。

界面文案遵循“结论 → 影响 → 行动”：先说明系统是否可用，再说明受影响与仍可用能力，最后给出恢复、重试或诊断入口。避免用问候语、营销标题、孤立错误码或重复的“当前”占据首屏；服务名、`trace_id` 和协议错误码保留稳定标识，解释和操作使用简洁中文。

## 2. 固定信息架构

一级域固定为：

| 一级域 | 主要任务 | 典型内容 |
|---|---|---|
| 对话 | 与当前角色持续交流并理解能力降级 | 消息流、输入、发送状态、语音入口、当前能力提示 |
| 概览 | 判断系统是否健康并进入异常对象 | 总体状态、runtime、Provider、关键告警、启动与资源摘要 |
| 能力 | 管理可用能力及其生命周期 | Extension、Skill、Provider 列表/主体与按需详情 |
| 活动 | 查找问题并追踪一次行为 | 错误优先事件流、筛选、`trace_id`、暂停、导出、详情 |
| 设置 | 修改受控配置并理解生效语义 | 模型与路由、语音、记忆、安全、存储、更新子域 |

只保留一层全局导航。二级导航只在设置等具有真实子域的页面出现；顶部不重复同一组选项。Context Drawer 仅在用户选中 runtime、日志、Extension、Provider 等对象时出现，关闭或未选中时不占据主工作区。

## 3. 已确认视觉输入

- 主题骨架：深色就是中性深色，浅色就是中性白色/浅灰；canvas、workspace、主要 surface 和正文层级不从蓝色、绿色或其他强调色派生。
- 强调色槽：用户已选择“青曜”作为 M11 目标强调色；它以偏蓝暗部、青绿核心与浅青晶光形成宝石内光，用于选择、focus、主要行动、链接和少量品牌时刻，不能覆盖大面积背景。精确视觉色阶见 [UI Design Tokens Reference](../../reference/ui-design-tokens.md#41-已确认的色彩方向)。
- 长期底色：参考用户提供的 Obsidian 深浅主题截图中连续、安静、协调的中性黑/白/灰关系，不复制其插件布局、导航或具体采样色。
- 深浅主题：两者必须来自同一中性语义映射；浅色不是把深色逐项调亮，深色也不是纯黑加霓虹，accent 另行映射。
- 感知目标：整体应具有“晶莹剔透”的清澈、含蓄光感和层次，而不是拟物成一块块玻璃。雾面、磨砂、半透明、柔和明暗面、局部内透光、微弱颗粒和低饱和反射都只是可组合手段。
- 背景自由：canvas 可以只有稳定底色，也可以带低对比环境轮廓或纹理；不能为了证明透明度而强制增加底图。没有底图时，仍可通过 surface 明度/不透明度差、内部光感、柔和阴影和局部色彩迁移建立通透层次。
- 边缘自由：玻璃式描边不是必需项。多数 surface 可以无边框或只保留极弱分隔；晶莹感优先由整体明暗、透光、材质过渡和交互反馈形成，不在所有边缘增加亮线。
- 材质边界：磨砂与透明用于解释层级和交互，不用每一行一个玻璃卡、全页同一透明度、强 glow、统一亮边或为了材质而牺牲文字对比。
- 禁止偏移：主题底色不转蓝或转绿，不用紫色渐变，不以大量青色霓虹、emoji、字符伪图标或组件库默认皮肤制造“未来感”。
- 信息层级：主要任务区最安静，异常和可行动状态比装饰更醒目；颜色不是唯一反馈。

参考图按证据角色使用：

| 参考图类型 | 吸收 | 不吸收 |
|---|---|---|
| Obsidian 深浅与透明主题截图 | 中性底色、长期舒适度、连续空间、雾面层与底层明暗的关系 | 插件布局、目录内容、导航结构、具体颜色、必须存在的底图 |
| 日程页面雾面材质截图 | 低饱和雾面层、柔和透光、明暗团块、整体晶莹而不锐利的感受 | 绿色主调、日历网格、分类彩色块、背景场景、页面文案 |

附件只提供视觉证据，不构成实现指令或运行时资产依赖；后续效果图和实现必须回到本简报的用户任务、信息架构与材质边界。

“青曜”强调色已确认并由 UI Reference 保存精确视觉基准；中性 theme palette、字体、圆角、阴影、surface 状态和 motion 仍待视觉比较，不在本简报复制数值。

## 4. 三个探索方向

三个方向使用相同页面内容、状态和信息架构，差异必须来自结构、密度、surface 与深度语言：

| 方向 | 核心意图 | 结构/材质 | 风险 |
|---|---|---|---|
| 静水工作台 | 长期安静、任务聚焦 | 连续 canvas、弱边界主工作区、舒适密度、按需 Drawer | 过度克制会缺少产品辨识度 |
| 晶光器皿 | 用有限材质表达“微光” | 中性底色上的清澈层次、雾面/透明可选、选择态内透光、精细高光 | 过量会滑向游戏/赛博 UI |
| 夜湖控制台 | 在诊断和配置中提高扫描效率 | 清晰分区、紧凑列表、主体 + Drawer、中高密度 | 容易退化成传统运维后台 |

这些名称只是比较标签，不构成主题名或实现 token。

## 5. 已确认视觉组合

用户已确认以下组合作为 M11 的最终视觉方向：

- 采用“静水工作台”的连续、安静结构；
- 采用 Obsidian 式中性炭黑/暖黑作为 canvas，而不是蓝黑 canvas；
- 采用“晶光器皿”的清澈层次和有限内透光；磨砂、透明、柔和明暗面按 surface 需要选择，不要求统一玻璃边框；
- 只在 runtime、活动和能力列表采用“夜湖控制台”的中等偏高密度；
- 深色、浅色和窄屏使用同一语义系统：中性 surface 承担长期阅读，青曜只承担选择、focus、主要行动、链接和少量品牌时刻。

该确认关闭视觉方向选择门，不把效果图直接当成生产 token。实现若偏离上述结构、材质或色彩边界，应先回到本简报核对，不用叠加 CSS 补救。

## 6. 代表页面设计合同

### 概览

概览代表方案必须同时表现全局结构、信息密度和有限材质：

- 单一左侧全局导航，图标与文字清楚，不再同时出现重复 Rail/Section Pane；
- 顶部只放产品身份、当前位置、总体健康和少量全局动作；
- 主体以总体状态摘要开场，随后是 runtime 列表、Provider/能力摘要和最近异常；
- canvas 可以是稳定纯色/渐变底色，也可以含低对比、非叙事性的环境轮廓、暗色图形或纹理；背景不是通透感成立的前置条件。采用背景内容时只保留大尺度轮廓和明暗，不让细节、主体或文字穿透到可读程度，也不得伪装状态或退化成壁纸展示；
- runtime 列表优先显示名称、readiness、简短原因和更新时间，不堆成等权卡片；
- 选中一个 runtime 时在右侧出现 Context Drawer，展示依赖、最近变化、诊断入口与可执行动作；
- 正常状态克制，`degraded/error` 比背景材质更醒目且有文字与行动出口。
- 首屏状态文案先给结论，例如“系统可用，1 项能力降级”；随后说明受影响服务和仍可用能力，主行动使用“查看恢复步骤”等结果明确的动词短语。

### 对话

- 消息流和输入是唯一主任务，不用状态卡片包围聊天；
- Provider/语音/连接降级以紧凑、可行动提示出现，不遮挡历史；
- 输入区覆盖发送、pending、失败重试、长文本、附件/语音能力不可用；
- Context Drawer 只在用户主动查看当前能力、记忆摘要或消息详情时出现。

### 设置

- 左侧或窄屏 Drawer 只列真实设置子域；主体一次只处理一个 owner；
- 字段说明、当前来源、Secret write-only、测试连接、revision 冲突和 reload/restart 结果保持可见；
- 保存区只在有脏状态时增强，不用永久悬浮大按钮争夺注意力；
- 危险操作与普通设置分区，提供明确后果、确认和恢复路径。

## 7. 组件与状态合同

首批组件族：

| 组件族 | 必须覆盖 |
|---|---|
| Global Navigation | 当前域、图标/文字、收展、窄屏入口、键盘与 focus |
| Health Summary | ready/degraded/failed、原因、仍可用能力、行动入口 |
| Resource List | 零项、单项、大量、长名称、未知值、部分失败、选择 |
| Context Drawer | 打开/关闭、`Escape`、scrim、焦点进入/返回、窄屏覆盖 |
| Feedback | loading/empty/degraded/error/pending/success，颜色外的图标与文字 |
| Form Field | label、说明、校验、disabled、Secret、脏状态、冲突 |
| Action/Confirm | 普通/主要/危险、pending、防重复、确认或 Undo |
| Conversation Composer | 多行输入、发送、失败恢复、能力不可用、键盘行为 |

React 组件 API 应优先表达真实语义，避免以大量 boolean props 拼装外观。只有多个组件共享状态和结构时才采用 compound component；受控/非受控模式必须明确，不能由 effect 在两套事实之间同步。

## 8. 容量、主题与可访问性

设计比较使用以下验证视口，不把它们直接写成 CSS breakpoint：

| 场景 | 验证尺寸 | 设计要求 |
|---|---:|---|
| 宽屏 | `1440 × 920` | 全局导航 + 主体；选中对象时可并列 Drawer，主任务仍有足够容量 |
| 临界宽度 | `1024 × 800`、`900 × 800` | Drawer 改覆盖或关闭，导航收敛，内容不被双侧栏挤压 |
| 窄屏 | `480 × 900` | 单列主任务，导航与详情按需覆盖，操作不依赖 hover |
| 缩放 | 200%、400% | 信息、错误和主要动作不丢失；非二维内容不要求双向滚动 |

候选阶段用同一代表任务比较宽屏与窄屏；最终方向覆盖深色宽屏、浅色宽屏和窄屏关键页。所有可操作元素满足语义 HTML、键盘、可见 focus、触控目标、reduced-motion 和 WCAG 2.2 AA；自动 axe/ARIA snapshot 只能补充人工检查。

## 9. 设计产物与确认门

视觉方向选择门已完成：三个方向使用同一信息架构比较，用户明确接受混合方案，深色、浅色和窄屏代表视觉已确认。进入首个 React 实现 slice 时必须继续完成：

1. 将已确认方向转为经过对比度验证的主题 palette、typography、spacing、radius、surface、motion、control sizing 和 capacity token；
2. 为最终方向补齐对话、概览、设置的宽/窄屏与关键状态场景，不再生成已淘汰方向的整页矩阵；
3. 固定首批组件族、stories、状态 fixtures 与截图名称；
4. 确保 Storybook stories/组件测试可独立运行；若试点 MCP，固定兼容版本、权限、fallback、收益指标和删除条件；
5. 用一项代表页面记录 Skill 前后首次正确率、虚构 API、交互/a11y 缺陷、视觉回归和纠偏轮数，确认新增规则确有收益。

用户确认授权的是上述视觉方向，不是未验证的生产实现。Shell/Router slice 可以在新执行会话中开始，但必须以本节 token、状态、组件和验证门作为完成条件。
