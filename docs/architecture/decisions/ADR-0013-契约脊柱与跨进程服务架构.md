## Context

当前 `protocol/` 以 JSON Schema 集中维护跨语言模型、配置、IPC envelope 和部分运行时 helper，并生成 TypeScript、Python 与 Unity C# 投影。它解决了手写镜像漂移，但也把“可调用服务”“事件”“配置文档”“SDK 模型”和“传输实现”放在同一个万能 Protocol 概念下。Kernel ↔ Cognition 使用 ZMQ 自制 RPC，Engine 使用 stdio 命令协议，Surface 与 Host 还存在手写 WebSocket 主线；`type + payload:any` 一类信封无法在编译期表达方法、方向、deadline、取消、错误和流的语义。

Glimmer Cradle 同时包含 TypeScript Kernel/Desktop、Python Cognition/Engine、C# Avatar、多进程本地监督、多个 Surface、Extension Host 和高频媒体器官。继续扩展当前 envelope 会让边界能力、领域模型和传输细节互相污染；把全部结构改成一种 IDL 又会损害配置、Character Package、manifest 和动态参数等文档型契约的可编辑性。

[ADR-0009](./ADR-0009-本地监督树与动态端点治理.md) 已固定 Kernel 监督权、回环动态端点、独立崩溃域、真实 readiness 和进程树回收。本决策只固定其上的长期契约与服务神经系统，不把动态端点改成固定端口，也不允许器官横向自由调用。

## Decision

### 1. 以 `contracts/` 重建契约脊柱

长期目标是删除万能 `protocol/`，以职责清晰的 `contracts/` 作为跨边界契约源头。目标物理形态为：

```text
contracts/
├── buf.yaml
├── buf.gen.yaml
├── proto/
│   └── glimmer/
│       ├── common/v1/
│       ├── kernel/v1/
│       ├── cognition/v1/
│       ├── surface/v1/
│       ├── avatar/v1/
│       ├── engine/audio/v1/
│       └── extension/v1/
├── json-schema/
│   ├── config/
│   ├── character/
│   ├── extension/
│   └── skill/
└── compatibility/
    └── README.md
```

目录表达 owner 和兼容世代，不按语言或传输复制同一消息。具体包拆分、生成插件和语言输出目录由 M12 工程验证决定，但不得改变“同一消息只有一个权威 IDL”的原则。

### 2. Protobuf Service 拥有可调用跨进程能力

跨进程 Command、Query 和 Stream 使用版本化 Protobuf Service 定义；核心器官内部通信以 gRPC 为默认目标。应用发布版本与契约兼容世代分离：应用 `v0.x` 可以消费 `glimmer.*.v1`，只有无法在同一兼容世代演进的破坏性语义才引入 `v2`。旧字段号和枚举值不得复用。

Kernel 是服务拓扑、监督、路由、权限、Ingress 和 Projection owner：

- Kernel 通过受管 client Adapter 调用 Cognition、Audio、Avatar 和 Extension Host 的专用 Service；
- 器官不发现或直连其他器官；跨器官协作回到 Kernel；
- Web/Desktop Surface 只访问 Kernel 专用 `SurfaceGatewayService`；
- 浏览器目标优先使用 Connect；不得把 Cognition、Engine、Avatar 或 Extension 内部 Service 暴露给浏览器；
- Surface Gateway 是面向产品表面的 BFF/Projection 边界，不成为领域事实源。

该拓扑复用 ADR-0009 的动态回环端点 catalog、owner PID、purpose 校验、进程隔离和监督回收。gRPC/Connect 是端点上的契约与调用语义，不是新的固定端口或外部公开网络。

### 3. JSON Schema 继续拥有文档型契约

配置、Character Package、Extension manifest/package、动态 Skill/tool 参数以及其他需要人工编辑、局部校验或开放扩展的 JSON/YAML 文档继续由 JSON Schema 拥有。每份 Schema 必须声明 dialect、稳定 `$id`、owner 和兼容策略。

Protobuf 消息可以引用文档的稳定标识、版本、摘要或 typed reference，但不得复制同一文档结构形成第二事实源。动态参数若由 JSON Schema 定义，Protobuf 只承载 schema reference 与受控 JSON value；若某个结构已由 Protobuf 定义，则不得再手写等价 JSON Schema。

### 4. 领域模型不进入契约脊柱

Kernel、Cognition、Avatar、Engine 和 Extension 各自拥有领域模型、状态机与业务不变量。生成 DTO 只允许出现在边界 Adapter：

```text
domain/application model
  <-> inbound/outbound Adapter
  <-> generated contract DTO
  <-> gRPC / Connect transport
```

业务层不得依赖生成 stub、transport context 或 Protobuf DTO；跨边界消息也不得泄露 Electron、provider SDK、Unity/Cubism、数据库 row、进程句柄或 UI view model。

### 5. 契约只使用五类明确语义

删除 `type + payload:any` 万能信封，所有跨边界契约归入：

| 类别 | 语义 | 典型形态 |
|---|---|---|
| Command | 请求 owner 执行有副作用动作 | unary RPC；返回受理/结果，不暗示幂等 |
| Query | 读取 owner 的事实或 Projection | unary RPC；无业务副作用 |
| Event | 已发生事实的不可变通知 | typed event + 订阅/投递语义 |
| Stream | 有序、可取消、具背压或流控需求的数据序列 | server/client/bidirectional streaming |
| Document | 可独立存储、编辑和校验的配置或 package 文档 | JSON Schema |

Command 不伪装 Event，Event 不充当 Query，Stream 不塞进重复 unary envelope，Document 不因为跨进程传输就复制为第二份 Protobuf 事实源。

### 6. 控制面与数据面分离

普通 RPC 只承载控制、元数据、小型结构化结果与 typed reference。大型音频、图像、模型、Avatar 帧批次和 Blob 使用以下受管数据面之一：

- 有界 gRPC/Connect stream；
- 带 owner、media type、size、digest、expiry 和访问范围的 Blob lease/reference；
- 经平台验证后采用的 shared memory 或专用本地数据通道。

普通消息不得内嵌无界 base64、模型文件或大型二进制。数据面失败不能伪造控制面成功；控制面返回的 reference 必须能表达未就绪、过期、取消和清理结果。

### 7. 一等调用与可观测语义

每个 Service 方法必须固定：

- request/response 或 stream 方向；
- deadline/timeout owner 和默认上限；
- cancellation 传播与停止工作规则；
- 稳定错误 code、可安全展示的 message 与可重试性；
- trace metadata；
- causation/correlation 标识；
- 身份、权限和进程世代；
- readiness 前置条件与 degraded 行为；
- 幂等键或明确的非幂等语义（如适用）。

gRPC status 表达传输与通用调用结果；领域失败使用稳定 typed detail，不靠自由文本分支。deadline 到期或取消后，服务端和所有上游调用必须停止无用工作。trace 解释机器链路，causation 解释角色生命因果，二者关联但不合并。

成功表示方法承诺的结果已经成立；accepted/pending 只能表示被受管流程接管，并必须提供可查询状态。失败不得留下不可解释的半提交。可选器官失败可以 degraded，但必须撤销不可用能力并更新 Kernel Projection；required 能力失败阻止对应 Ingress。重试只用于明确可重试且满足幂等条件的调用。

### 8. 兼容与验证门禁

契约演进必须同时经过：

- Buf lint 和 `buf breaking`，以固定基线检查 Protobuf wire/source 兼容；
- JSON Schema dialect、fixture 和项目定义的 compatibility 检查；
- TypeScript、Python、C# 跨语言 serialization round-trip；
- 每个边界 Adapter 的 contract test；
- 服务成功、typed failure、deadline、cancellation、metadata、readiness 和 generation mismatch 测试；
- 目标 Surface 的 Connect/gRPC-Web 兼容测试（若该方法暴露给 Surface）。

生成物可复现且只读。契约版本升级必须有 producer/consumer 顺序、可观测迁移状态、删除条件和回退边界。

### 9. 分阶段迁移且不永久双轨

M12 按以下切片推进；每一步只有满足删除条件才结束：

1. **骨架与基线**：建立 `contracts/`、Buf/JSON Schema 兼容门和多语言最小生成验证。此阶段不改变运行主线。
2. **Kernel ↔ Cognition**：先定义 Service 与 Adapter contract test，再迁移调用。新链路通过真实启动、deadline、取消、错误、trace、readiness 和恢复门后，删除对应 ZMQ 自制 RPC、万能 IPC envelope 与旧生成入口。
3. **Kernel ↔ Engine/Avatar/Extension Host**：逐边界迁移。每条新链路通过受影响器官实机/集成门后，删除被替代的 stdio 命令协议或手写 WebSocket 主线。
4. **Surface Gateway**：Desktop/Web 只消费 Kernel Projection 与 Command/Query/Stream；浏览器 Connect 与 WebSocket 的最终分工经验证后固定。目标路径通过认证、断线、背压、取消和页面状态门后，删除被替代的手写 Surface WebSocket 主线。
5. **物理收口**：所有消费者停止引用 `protocol/`，生成、测试、配置和文档切到 `contracts/` 后删除旧目录、兼容桥和迁移 feature flag。

迁移期桥接只允许有唯一 owner、观察指标、删除条件和最迟阶段；不能成为长期可选 transport。平台级阻断必须由新的 ADR 修改本决策，不能静默回退到旧架构。

### 10. 工程验证项不构成已落地事实

以下方向已受本 ADR 约束，但具体实现仍需 M12 以 spike/contract test 固定：

- Node/Python/C# 的 gRPC、Connect 实现与代码生成插件；
- Windows/Linux 本地端点与进程认证；
- Connect streaming 与 WebSocket 的最终分工；
- Audio/Avatar 数据面的 streaming、Blob lease 或 shared memory 阈值；
- 迁移切片的性能、内存、启动和包体基线。

验证可以调整插件、阈值和切片顺序，不能在无新 ADR 的情况下否定 Contract Spine、Kernel 拓扑和单一事实源。

### 11. 标准、治理、供应链与厂商锁定

本决策采用的概念与技术不处在同一层，必须准确表述：

| 对象 | 性质与治理 | 在摇篮中的位置 |
|---|---|---|
| DDD、Hexagonal Architecture、BFF/Projection、Saga、control/data plane | 架构模式与设计方法，不是某个产品或协议 | 用于划分 owner、Port/Adapter、Surface 聚合、跨边界补偿和媒体通道 |
| Protobuf | Google 发起并持续主导、采用 BSD 风格开源许可的 IDL/序列化生态；语言与 wire format 有公开文档并可由第三方实现，但官方明确说明它不是任何标准组织的正式标准 | 默认 Service IDL 与结构化 wire contract；不得描述为 ISO、IETF 或其他组织标准 |
| gRPC | Google 发起、现为 CNCF 项目、主要实现采用 Apache-2.0 的开放 RPC 框架与协议生态 | 核心器官 Adapter/Transport 的默认实现；不是专有云服务 |
| JSON Schema | 由开放社区协作维护的 JSON 文档描述与校验规范，有公开 specification、dialect 和实现生态 | 文档型契约的权威语言 |
| Buf CLI | Buf 发起、Apache-2.0 的开源 Protobuf 工具链 | 本地 lint、breaking、generate 的默认工具；不要求使用托管服务 |
| Connect | Buf 发起、Apache-2.0 的开源 RPC 协议/实现家族，并可与 gRPC/gRPC-Web 互操作 | 浏览器 Surface Gateway 的优先 Adapter/Transport；不是私有云服务 |
| Buf Schema Registry 及其他托管能力 | 可选 SaaS 或外部服务，不是本架构事实源 | 不得成为构建、生成、兼容检查、开发、发布或运行的必需依赖 |

防锁定规则固定为：

1. canonical `.proto` 与 JSON Schema 全部保存在本仓库；代码审查和 Git 历史是契约变更依据。
2. Buf、`protoc`、语言插件、gRPC/Connect runtime 与 JSON Schema validator 版本必须固定；生成链能在无专有云注册表的环境离线复现。
3. 外部依赖的源码、许可证、摘要与获取方式进入供应链清单；远程插件或托管 SDK 只能作为可选加速，不能成为唯一生成入口。
4. Domain/Application/Port 不 import gRPC、Connect、Buf、Protobuf runtime 或生成 DTO；这些依赖只存在于 Adapter、Transport 和 composition root。
5. gRPC 与 Connect 是默认实现，不是领域边界本身。替换 transport/runtime 只允许修改 Adapter、装配、部署和对应 contract test，不应修改领域模型或业务 Port。
6. 兼容基线必须能从 Git commit/tag 或仓库内 artifact 计算；`buf breaking` 不依赖 BSR 才能运行。
7. 如果某个实现开始要求专有控制面、不可导出的 Schema、在线代码生成或供应商特有领域类型，迁移必须停止并重新审查。

## Consequences

- 跨进程能力从“能传 JSON”提升为可审查的版本化 Service，方法、方向、错误、deadline、取消和流语义进入契约。
- DDD/Hexagonal Architecture 保持领域 owner 与 Adapter 边界；IDL-first 负责跨语言可生成契约；gRPC 负责器官 RPC；Connect 负责浏览器友好的 Surface Gateway；Buf 和 JSON Schema compatibility 分别治理两类 IDL；BFF/Projection 保护 Surface；control/data plane 分离保护媒体热路径。这是成熟方法的组合，不是复制某个厂商模板。
- 该组合适合 TS/Python/C#、本地多进程、Kernel 监督、多个 Surface、Extension 和媒体器官：语言绑定由生成器处理，进程崩溃域仍由 Kernel 治理，浏览器只看专用投影，文档型扩展仍保留开放性。
- 代价是生成工具链、Adapter、兼容基线和 contract test 增加；团队必须维护明确 service owner，而不能把所有消息塞回一个 bus。
- M12 已按本决策删除 `protocol/`、ZMQ、stdio RPC 和被替代的器官间手写 WebSocket；历史迁移窗口只保留在 Git 与里程碑证据中，不是当前可选主线。

## Alternatives considered

- **全部使用 JSON Schema**：适合文档校验，但不能自然拥有版本化方法、stream、deadline、取消、status 和多语言 service stub；拒绝作为 RPC 主干。
- **全部使用 Protobuf**：会把配置、Character Package、manifest 和动态参数变成不易编辑、扩展和独立校验的消息；拒绝作为文档契约唯一工具。
- **内部全部 REST**：HTTP 资源模型适合公开资源 API，但器官之间存在双向 stream、取消、严格方法和生成 client 需求；不作为核心器官默认目标。
- **万能 Event Bus**：Command、Query、Event、Stream 的交付、响应、顺序和失败语义不同；统一 bus 会隐藏 owner、deadline 和调用结果。
- **长期维护自制 ZMQ RPC**：需要自行维护 discovery、stub、status、取消、deadline、stream、兼容和跨语言工具链，重复成熟 RPC 生态能力。
- **Surface 直接访问各器官**：减少一跳但破坏 Kernel 权限、监督和 Projection owner，并扩大浏览器信任边界。
- **Protocol 与 Contracts 永久并存**：形成双事实源和双主线；只允许受删除条件约束的迁移窗口。
