# ADR-0015：工程自动化平面与交付生命周期分层

## Context

Glimmer Cradle 已经把 Cognition、Kernel、Avatar、Engine、Extension、Contracts、Data 与产品 Surface 视为需要长期 owner、边界、生命周期和验证的架构构件，但 Scripts、Automation、CI、Build、Release、Install 与 Ops 仍容易被理解为功能实现后的辅助工具。这种分层不完整：多语言、多产品、多进程、跨平台和本地优先的运行架构，只有在源码能够经可复现任务、同构 CI、固定制品和可恢复宿主事务抵达用户环境时，才具备持续演化能力。

固定状态上的 Scripts 审查已经暴露出结构性风险类别：宿主事务缺少全局串行化、被替换进程可能发起自替换、不同恢复目的的备份共享清理域、Smoke 接触真实数据、DLQ “重放”与删除语义不一致、状态查询提前产生权限副作用、本地与 CI 缺少同一公共门、root 与 package prehook 重复工作、领域任务集中在 root、发布与供应链证据不完整，以及 Desktop 缺少独立产品打包矩阵。这些审查结论是 M13 的输入证据，不表示目标能力已经实现。

工程生命周期平面服务所有运行时器官，但它不是角色运行时器官。把它并入认知核、中枢监督树、身体、能力生态或记忆脊柱，会混淆“系统如何运行”和“系统如何被构建、交付、安装、恢复”；把它留作散落脚本，又会让每个运行时架构决策在交付边界失去可验证性。

本决策固定长期分层、owner、任务契约和不变量；当前命令、目录、workflow 与操作事实仍由 Current、Implementation、Reference 与 Guide 描述，落地差距由 M13 承担。

## Decision

### 1. 工程生命周期是一等平台承重面

Scripts、Automation、CI、Build、Release、Install 与 Ops 共同组成工程生命周期平面。它与运行时架构同等需要：

- 唯一 owner 与写入边界；
- 输入、输出和副作用契约；
- 成功、失败、取消、恢复与清理语义；
- 本地、CI、发布、安装和宿主环境的验证证据；
- 可替换实现和旧入口删除门。

该平面服务 Contracts、Kernel、Cognition、Desktop、Avatar、Engine、Extension、Data 和产品组合，但不拥有它们的业务或角色语义，不进入角色运行时监督树，也不成为新的万能业务层。

### 2. 单向交付链与分层 owner

长期链路固定为：

```text
source
  -> owner-local atomic task
  -> repository thin orchestration
  -> CI
  -> fixed artifact
  -> install / ops
```

各层职责固定如下：

1. **Package-local owner 拥有原子任务和领域语义。** package、product、host、contract 或数据工具 owner 定义本领域的 build、check、prepare、package、migration、smoke 等原子任务；任务实现与受影响源码保持物理邻近。
2. **Root 只做真正跨仓薄编排。** root 可以固定公共命令、依赖顺序和聚合 exit status，但不得复制 owner-local 业务逻辑，也不得用隐式 prehook 重复执行同一任务。
3. **Workflow 只调用公共任务。** CI/Release workflow 负责事件、权限、runner、cache、artifact 上传和证据保存；不得在 YAML 中重写本地不存在的业务逻辑。
4. **CI 固定 source 到 artifact 的证据。** PR 与发布门都从干净 fixed source 调用公共任务；平台差异必须显式进入矩阵，不以某个开发者机器的隐式环境为基线。
5. **Release 只消费 fixed artifact。** Release 输入必须有版本、manifest、digest 和 provenance/attestation；发布阶段不得重新解释漂移源码或悄悄产生另一份未验证制品。
6. **Install/Ops 由 host-global transaction owner 串行化。** 同一宿主上的安装、更新、重启、备份、恢复、回滚、卸载和清理必须取得同一全局锁或等价事务租约；跨进程 handoff 先把操作交给不会被本次替换回收的 owner，再终止旧进程。

每层只能增强证据和环境接入，不能反向接管前一层的领域 owner。

### 3. 所有任务具备可验证契约

每个公共任务必须能够声明并验证以下字段；具体表达可以是 manifest、代码类型、CLI help、结构化输出或组合形式，但不得只存在于维护者记忆：

| 契约 | 要求 |
|---|---|
| `inputs` | fixed source、配置、依赖、平台、凭据引用与前置 artifact；隐式环境必须归零或显式化 |
| `outputs` | 文件、目录、manifest、digest、报告或明确“无持久输出” |
| `side effects` | 文件、权限、网络、token、进程、容器、数据库和宿主状态变化 |
| `lock` | 需要的 owner-local、repository 或 host-global 锁及争用失败语义 |
| `idempotency` | 同一 fixed input 重复执行的结果、去重键或明确非幂等边界 |
| `confirm` | 高风险动作的显式确认入口；非交互环境缺确认时必须拒绝 |
| `dry-run` | 不提交副作用的计划/诊断路径；不能借 dry-run 提前创建状态 |
| `exit code` | 稳定区分成功、验证失败、前置缺失、锁冲突、用户拒绝和恢复失败 |
| `log/diagnostic` | 结构化阶段、owner、trace/correlation、脱敏摘要和恢复入口 |
| `cleanup/recovery contract` | 成功、失败、取消和进程中断时的临时资源回收、补偿、回滚或人工恢复终态 |

Query、status、logs、doctor 与 dry-run 默认无业务副作用；如果读取必须准备临时资源，该行为也必须显式、最小权限、可清理，且不能创建长期 token、env 或 state。

### 4. 本地与 CI 同构

- 本地开发、PR CI、tag Release 和发布前验证调用同一公共任务入口；
- workflow 只提供事件与环境装配，不能拥有另一套校验逻辑；
- package prehook 与 root orchestration 不得重复构建同一依赖；task graph 必须能解释依赖、缓存和输出；
- Windows/Linux 基础门使用相同任务语义，平台 wrapper 只做 shell、路径、权限和进程接入；
- encoding、workspace、ignore、deploy、contracts 等仓库级 inventory 必须完整，不能只检查最常见源码目录；
- prepare 类任务必须输出可验证 manifest/digest，不能只依赖 sentinel 文件判断成功。

### 5. 跨平台 core 与 thin wrapper

任务的领域语义和事务状态机应由跨平台 core 持有；PowerShell、Bash、workflow step 或平台服务 wrapper 只负责：

- 参数和环境变量接入；
- 路径与 shell 差异；
- OS 权限、进程、服务管理和 signal 转换；
- 调用公共 core 并原样传播结构化结果与 exit code。

不能以某个 shell 隐式存在为公共任务前提，也不能在两个 wrapper 中分别维护同一业务状态机。

### 6. 固定制品、供应链与最小权限

- Base image、外部工具、依赖与 builder 使用可审计的固定版本和 digest；
- tar、OCI、Desktop installer 等每类产品制品都有独立 manifest、digest、provenance/attestation 与验证入口；
- Release 不把 checksum 当作全部来源证明；校验必须能独立验证制品与 fixed source/构建身份的关系；
- CI、Release、Install 与 Ops 只取得当前阶段所需的最小权限；查询路径不提前扩大权限；
- Personal Server 与 Desktop 是独立产品矩阵，各自固定输入、输出、支持平台和验收门；一个产品的 Release 不隐式代表另一个产品已经可交付。

### 7. 事务安全、数据安全与恢复语义

- 同一宿主只允许一个 install/ops transaction owner；
- 需要更新自身承载的 Ops Bridge、service 或 container 时，必须先完成外部 handoff，再由稳定 owner 继续事务；
- manual、transaction 和 restore-safety backup 具有不同 retention owner 与清理规则，不得混合淘汰；
- Smoke 使用隔离数据、模型和 package 投影，不通过可写链接接入真实用户域；
- DLQ replay 表示 payload 已经重新提交给真实处理链并得到可追踪结果；resolve 表示人工确认终态；cleanup 只能按 retention 清理已满足删除条件的证据；
- diagnostic/show 默认脱敏，查看 raw payload 或 stack 需要显式高权限和审计。

### 8. Owner-local 物理收口与旧入口删除

Avatar、Personal Server、Data tooling、Desktop packaging 等任务实现归所属 owner。Root 只保留稳定公共 wrapper 和跨 owner 编排。迁移切片必须列出旧入口、调用者、回退窗口、观察指标和删除条件；新入口通过 local/CI、产品构建和安装/恢复门后，删除旧 root 实现、重复 prehook、workflow 私有逻辑和兼容 wrapper。

工程生命周期平面不允许用文档把旧脚本解释成新架构。目录、命令、task graph、workflow、artifact manifest、安装事务、测试与操作文档必须在实现切片中一起收口。

### 9. 工具可替换，工具不是架构目标

本决策不选择 Nx、Turborepo、Taskfile 或任何特定 task runner 作为长期架构目标。实现可以继续使用现有工具，也可以在证据充分时替换；工具选择必须服务于 owner-local tasks、薄编排、local/CI parity、fixed artifact、结构化诊断和删除旧入口，不能为了采用流行工具重写领域任务或制造永久迁移层。

## Consequences

- 工程生命周期从“脚本集合”成为可审查、可测试、可演化的平台承重面；运行时架构决策能够沿同一链抵达固定制品与宿主。
- Package owner 同时拥有实现与原子工程任务，领域语义不再被 root 或 workflow 复制；root 和 CI 更薄、更稳定。
- 本地与 CI 的差异缩小，PR 可以在 Release 前阻断编码、跨平台、依赖图和制品问题。
- Release、Install 与 Ops 获得固定输入、宿主级串行化、最小权限、失败终态和恢复证据；自替换、半提交和误清理风险下降。
- 代价是需要为现有任务补齐契约、输出 manifest、结构化诊断、跨平台 core、PR 门、供应链证据和分层测试，并迁移/删除重复入口。
- 接受本 ADR 不表示当前 Scripts、workflow、Build、Release、Install 或 Ops 已经满足这些要求。Current、Implementation、Reference 与 Guide 在 M13 实现切片落地前继续描述当前事实。

## Alternatives considered

- **所有逻辑堆在 root scripts**：入口集中但 owner 与领域语义远离源码，root 会持续增长为第二业务层，跨产品和跨平台改动互相牵连；拒绝。
- **Workflow 重复业务逻辑**：短期看似直接，长期造成只能在 CI 复现的第二事实源，本地/CI parity、dry-run、诊断和工具替换都失效；拒绝。
- **Package、root 与 prehook 多次执行同一任务**：不能用“更保险”解释重复构建；它隐藏 task graph、浪费时间并可能消费不同中间状态；拒绝。
- **Release 从源码现场重建**：发布输入会随环境、依赖和权限漂移，无法证明本地/CI 验证过的就是最终制品；拒绝。
- **每个 deploy/ops 入口各自管理锁和恢复**：同一宿主会出现竞态、自替换与备份/恢复冲突；拒绝，必须有 host-global transaction owner。
- **为 Nx、Turborepo、Taskfile 或其他流行工具重写**：工具不能替代任务契约、owner 和 fixed artifact；只有现有实现无法满足明确门禁且迁移有删除条件时才允许替换。
- **把工程生命周期并入角色运行时脊柱**：会混淆角色语义、运行监督与交付事务，导致 Kernel/Cognition 或器官 owner 承担仓库/宿主工程职责；拒绝。
- **继续作为 candidate/backlog 零散修补**：用户已经承诺补齐该承重面，且风险跨越 Build、Release、Install 与 Ops，不能用互不相干的候选项收口；拒绝，统一由 planned M13 承担。
