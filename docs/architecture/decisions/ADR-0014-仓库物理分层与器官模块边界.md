## Context

当前仓库已经有 `core/`、`engines/`、`products/`、`packages/`、`native/` 和 `protocol/` 等根目录，但目录层级还不能稳定表达长期 owner 与崩溃域：具体 Unity 承载与 Avatar 领域混在 `core/avatar/unity-host/`；Extension 第三方代码的进程承载仍位于 Kernel 源码内部；Kernel 的 `foundation/`、`application/services/`、`infrastructure/`、`host/` 与生命周期目录存在职责交叠；Cognition 的领域模块、技术目录和 `protocol/generated/` 平级。

这些问题不能靠重命名文档解决。Glimmer Cradle 同时包含 TypeScript Kernel、Python Cognition、C# Avatar Host、多个产品 Surface、第三方 Extension 和本地媒体进程，需要让“领域 owner”“进程承载”“产品装配”“公开开发包”“契约源”和“平台热路径”在物理结构上可区分，同时保留 Kernel 与 Cognition 各自的单进程一致性边界。

[ADR-0013](./ADR-0013-契约脊柱与跨进程服务架构.md) 已固定 Contract Spine、跨进程 Service/Transport、Kernel 星形服务拓扑和 Surface Gateway；[ADR-0009](./ADR-0009-本地监督树与动态端点治理.md) 已固定本地监督树、动态端点、真实 readiness 和 Kernel 监督权。本决策与两者正交组合，只拥有仓库根职责、器官内部分层、Host 物理归属、进程内/跨进程事务边界和迁移删除门。

## Decision

### 1. 根目录按 owner 与物理职责分层

长期目标根职责树固定为：

```text
core/          # 领域器官与平台中枢
engines/       # 官方模型与媒体资源执行器
hosts/         # 具体进程承载、语言/框架入口与崩溃域
products/      # Desktop、Personal Server 等产品组合
packages/      # 稳定跨产品或第三方消费的公开开发包
contracts/     # 跨语言、跨进程契约源
native/        # 平台原语、ABI/FFI 与性能热路径
configs/       # 配置事实源
assets/        # 随版本发布的只读默认资产
data/          # 本机状态、模型、包、缓存、工作材料与可观测性
deploy/        # 部署与安装描述
scripts/       # 工程自动化入口
docs/          # 项目事实源
```

该树是目标形态，不是当前目录声明。当前仍存在 `protocol/`，尚无目标 `hosts/`，且 Avatar/Extension Host 仍在旧 owner 下；Current 与 Implementation 在迁移完成前必须继续如实描述这些现状。

职责规则如下：

| 根 | 拥有 | 不拥有 |
|---|---|---|
| `core/` | Kernel、Cognition、Avatar 等领域模型、Application、Port、器官不变量及器官自身唯一进程入口 | 需要与领域分离的 Unity/Electron/provider 等具体 Host 实现 |
| `engines/` | 官方模型/媒体资源执行和自身资源 readiness | 人格判断、全局监督、第三方扩展 |
| `hosts/` | 需要与领域 owner 分离的具体进程入口、framework bootstrap、不可信代码崩溃隔离和边界 Adapter 装配 | 被承载器官的领域事实与策略 |
| `products/` | 产品 composition、产品专属页面、流程和发布入口 | 可复用领域事实或第三方 SDK |
| `packages/` | 公开 SDK、稳定跨产品库或可独立测试和版本治理的包 | 领域内部实现和暂时重复代码 |
| `contracts/` | ADR-0013 定义的 canonical Protobuf/JSON Schema 与兼容治理 | 领域模型、业务 Port 和 transport runtime |
| `native/` | 平台原语、ABI/FFI、合成与经证据下沉的性能热路径 | 产品与角色业务语义 |

`configs/`、`assets/`、`data/`、`deploy/`、`scripts/` 和 `docs/` 延续各自既有明确职责，不作为内部实现的兜底目录。

根级 `hosts/` 不要求把每个进程入口都从 owner 中抽走。Cognition 的 `host/` 是 Cognition 自身唯一进程的入口和装配边缘，继续留在 `core/cognition/`；UnityAvatarHost 必须与 Avatar 领域分离、Extension Host 必须隔离不可信代码，因此二者归根级 `hosts/`。是否进入根级 `hosts/` 由领域分离、独立构建/分发和崩溃隔离事实决定，不能只因名称含 `Host` 就机械搬迁。

### 2. Kernel 保持单进程模块化中枢

Kernel 继续是单一 Stage Manager 和平台中枢，不拆成网络微服务。其内部长期收口为：

```text
core/kernel/
└── src/
    ├── domain/
    ├── application/
    ├── ports/
    ├── adapters/
    ├── runtime/
    └── composition/
```

- `domain/` 拥有 Kernel 的监督、权限、路由、Ingress、catalog 与 Projection 规则；
- `application/` 按明确 use case 编排领域能力，不设置无 owner 的 `services` 聚合；
- `ports/` 是 Kernel 业务边界需要或提供的接口，不 import transport/runtime；
- `adapters/` 实现 persistence、transport、process、observability、contract 等技术边界；
- `runtime/` 只承载生命周期监督、readiness、start/stop/restart 和进程世代语义；
- `composition/` 是唯一装配根，创建 Adapter 并接线 Application/Port。

当前泛化 `foundation/` 中的 config、event bus、logger、storage、process、endpoint 与 ingress 能力必须分别归入明确 Domain、Port、Adapter 或 Runtime owner；`application/services/` 必须拆到有名称的 use case/能力模块；transport、generated DTO 和进程句柄不得进入 Domain/Application。迁移完成后删除旧聚合目录和兼容 import，不以 re-export 外壳永久保留旧路径。

### 3. Cognition 是单一心智主权的模块化单体

Cognition 长期保持一个独立受 Kernel 监督的进程，同时保持单一心智主权和单一一致性边界。`identity`、`persona`、`affect`、`experience`、`memory`、`conversation`、`context`、`deliberation`、`volition` 是同一 Cognition 内的领域模块，不是可独立发现或远程调用的微服务。

其内部长期收口为：

```text
core/cognition/
└── src/glimmer_cradle/cognition/
    ├── domain/
    ├── application/
    ├── ports/
    ├── adapters/
    └── host/
```

- `domain/` 按心智领域模块组织实体、值对象、策略与领域事件；
- `application/` 组织认知循环、维护、查询和跨领域 use case，并固定事务边界；
- `ports/` 表达 provider、persistence、clock、Kernel 边界等依赖能力；
- `adapters/` 承载 provider、transport、persistence、observability 和 contract DTO 映射；
- `host/` 只承载 Python 进程入口、装配和受监督生命周期接入。

领域模块可通过明确 Application use case 或 Port 在进程内直接协作，不因目录分域增加网络边界。generated contract DTO/stub 只能位于 contract Adapter 边缘；当前平级技术目录和 `protocol/generated/` 在消费者迁移完成后删除，不得成为心智内部模型。

### 4. 进程内事务与跨进程协作分层

同一进程、同一一致性边界内的跨领域协作优先使用本地 Application use case、明确事务边界和领域事件；不把内部模块交互包装成 RPC，也不通过共享 generated DTO 或万能 Event Bus 维持一致性。

只有跨进程、跨一致性边界的业务流程才使用显式 Saga/Process Manager。其 owner 必须定义步骤状态、幂等键、deadline/cancellation、causation/correlation、补偿、重试上限、超时后查询和可观测 Projection。摇篮不引入跨器官分布式数据库事务；某一步无法安全补偿时必须暴露人工恢复或失败终态，不能伪造原子成功。

Kernel 可以作为涉及多个受监督器官流程的 Process Manager，但不据此接管 Cognition、Avatar、Engine 或 Extension 的领域判断。ADR-0013 的 Command、Query、Event、Stream 和错误语义继续适用于跨进程边界。

### 5. Avatar 领域与 Unity 承载物理拆分

`core/avatar/` 必须成为真正的一等 Avatar 领域 owner，拥有 Avatar Package、State、Behavior 和 Ports；Unity/Cubism、进程 bootstrap、渲染 driver、Host 协议接入与 framework 生命周期属于 `hosts/` 下的具体 Unity Avatar Host。

当前 `core/avatar/unity-host/` 同时包含领域与具体 Unity 承载。M12 必须先建立独立 Avatar Domain/Application/Port，再把具体承载迁入 `hosts/`，修正 imports、程序集、composition root、生成物、配置、测试、构建和打包入口；所有消费者停止引用旧路径后删除 `core/avatar/unity-host/` 和旧构建入口。只移动目录或保留同构兼容壳不算完成。

具体进程身份继续使用命名规范已经固定的 `UnityAvatarHost`。本 ADR 不任意发明 `hosts/` 下的精确 leaf；实现切片必须根据最终 package/进程身份和仓库命名规范确定 leaf，并在同一切片同步 package、可执行文件、配置和文档。

### 6. Extension Host 是独立不可信代码崩溃域

执行第三方扩展代码的 Extension Host 物理位于 `hosts/`，作为受 Kernel 监督的独立进程和崩溃域。Kernel 只拥有：

- Host 进程监督与 readiness；
- 权限、激活策略和审计；
- manifest/contribution/skill catalog 与运行 Projection；
- 调用编排、deadline、取消和回收。

Kernel 进程不得加载或执行第三方 Extension handler。Extension Host 只通过公开 SDK、Host Port 和 ADR-0013 的边界契约访问平台能力；其崩溃、停用或升级必须撤销 handler、catalog、lease、timer、订阅和子进程。M12 迁移完成后删除 Kernel 内的旧 Extension Worker 承载入口与兼容进程协议，不删除仍由 Kernel 拥有的监督、权限、catalog 和编排模块。

具体进程身份为 `Extension Host`；精确 leaf 同样由实现切片按 package/进程身份确定，不能以 `worker`、`runtime` 等含混名称掩盖 owner。

### 7. Products 与 Packages 设提取门

`products/` 只组合器官、Host、Surface 与产品专属配置/页面/流程。Desktop 页面继续由 Desktop product owner 持有，Personal Server 页面继续由 Personal Server product owner 持有。

不提前创建 UI shared package。只有至少两个真实产品已经出现稳定复用，并且候选模块具备独立 API、版本兼容策略、测试与 owner 时，才允许把 design primitives 或 surface client 提取到 `packages/`。相似视觉或未来可能复用不构成提取依据。

所有进入 `packages/` 的内容必须至少满足一项：对第三方公开的 SDK；被多个真实产品稳定消费的库；可独立测试、版本与发布治理的开发包。领域内部实现、临时 Adapter、单产品组件和无 owner helpers 留在所属模块，不把 `packages/` 变成内部杂物抽屉。

### 8. 迁移必须删除旧物理主线

物理架构升级必须同时迁移目录、package 名、imports、composition root、生成物、配置、测试、构建、打包和文档。每个切片开始前列出旧路径、消费者、owner、观测指标、回退窗口和删除条件；完成时证明旧引用归零并删除旧入口、re-export、feature flag 和兼容桥。

迁移期间 Current/Implementation 只描述真实代码。完成一个切片后在同一变更中更新对应事实源；Blueprint/ADR 继续表达长期不变量，M12 保存未完成工作和验收门。任何平台级阻断都必须通过新 ADR 修改本决策，不得静默保留永久双轨。

## Consequences

- 领域器官、进程 Host、产品组合、公开包、契约源和 native 热路径在仓库根形成可审查的物理边界；目录可以直接回答 owner 与崩溃域。
- Kernel 与 Cognition 都保持模块化单体和本地一致性，不因 Contract Spine 或多领域模块被误拆为微服务；跨进程复杂度只用于真实进程边界。
- Avatar 领域不再被 Unity 实现吞没，Extension 第三方代码也不再与 Kernel 共用崩溃域。
- DDD/Hexagonal Architecture 用于领域模块、Application、Port 和 Adapter 边界；模块化单体保护 Kernel/Cognition 的一致性；Saga/Process Manager 只协调跨进程流程；BFF/Projection 与 control/data plane 仍由 ADR-0013 约束。这是适配摇篮多语言、本地多进程与多产品形态的模式组合，不是微服务或厂商目录模板。
- 代价是 M12 需要跨 package、imports、构建、测试和打包的机械迁移，并在短期内维护受删除门约束的桥接；迁移不能只做语义重命名。
- 当前目录仍是事实。接受本 ADR 不表示 `hosts/`、Avatar Domain 或新内部层次已经实现。

## Alternatives considered

- **按语言或框架划分仓库根**：会让 TypeScript/Python/Unity 成为业务 owner，难以表达器官与产品边界；拒绝。
- **把每个 Cognition 领域模块拆成服务**：增加网络失败、版本和分布式一致性成本，并破坏单一心智事务边界；拒绝。
- **把所有进程代码留在各领域目录**：领域模型会继续依赖 Unity、provider、transport 与进程 bootstrap；拒绝。
- **Kernel 内执行 Extension**：减少一个进程，但把不可信第三方代码带入全局监督中枢，无法形成可靠崩溃隔离；拒绝。
- **所有内部协作都走 Event Bus**：隐藏 Command/Query、事务 owner、失败和顺序语义，无法替代明确 use case 或 Saga；拒绝。
- **预建通用 UI/package 层**：在只有单一消费者时制造不稳定公共 API 和 owner 漂移；达到真实复用门之前拒绝。
- **只移动目录并保留旧 import 外壳**：不能消除依赖方向和双主线；只允许有明确删除条件的短期迁移桥。
