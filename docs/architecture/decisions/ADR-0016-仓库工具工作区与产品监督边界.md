# ADR-0016：仓库工具工作区与产品监督边界

- 状态：accepted
- 日期：2026-08-25
- 修订：[ADR-0014](./ADR-0014-仓库物理分层与器官模块边界.md) 的 root `scripts/` 物理落点，以及 [ADR-0015](./ADR-0015-工程自动化平面与交付生命周期分层.md) 的 repository thin orchestration 实现落点。

## Context

M13 收口后 root `scripts/` 只剩 architecture、encoding 与 Product Supervisor 三项长期跨仓工具。这个三文件快照把“当前数量”误写成了长期拓扑：architecture check 混合 repository invariant 与 Desktop、Personal Server、Audio、deploy 等 owner 行为；encoding 实际检查 UTF-8 与 BOM，却沿用 `no-bom` 实现名；Product Supervisor 反向 import Extension SDK 内部 pnpm helper，并让 Personal Server 经过 Desktop asset preparation。

这些工具具有独立 owner、CLI、失败语义与测试需求，但它们不是运行时 package、发布制品或新的业务层。继续把实现留在 root `scripts/` 会使 root 再次成为 owner 混合区，也无法在不硬编码文件数量的前提下演化。

## Decision

### 1. `tools/` 只作为 grouping root

长期跨仓工具进入 `tools/`，真实 owner 是叶子 workspace：

```text
tools/
├── repo-checks/
│   ├── package.json
│   ├── src/{architecture,encoding}/
│   └── tests/
└── workspace-supervisor/
    ├── package.json
    ├── src/
    └── tests/
```

叶子 workspace 必须 `private`、有独立 package name、`src/`、`tests/` 和稳定 CLI。`tools/` 不拥有逻辑，不限制未来合规工具数量，也不成为 `engineering/automation/conformance` 总桶。owner-local `scripts/`、`tools/` 或语言 CLI 继续留在直接 owner，不因可测试或可复用被吸入本 grouping root。

### 2. Root 只保留 package façade

Root `package.json` 保留用户稳定命令，通过完整 workspace package name 与 `--fail-if-no-match` 路由。root 不保留 `scripts/` wrapper，不复制工具逻辑，也不让工具回调 root façade 形成递归。

`@glimmer-cradle/repo-checks` 拥有 repository-wide invariant 与 tracked/inventoried text 的 UTF-8/BOM 检查；具体 Product、Desktop、Audio、deploy 行为由 owner-local tests 拥有。Architecture rules 模块化、可单测，并验证 required 工具存在而不限制 `tools/*` 叶子数量。

### 3. Product Supervisor 只拥有开发期故障域

`@glimmer-cradle/workspace-supervisor` 只拥有开发期产品组合启动、进程树、signal/exit 传播与 sibling shutdown。它自己解析 Corepack/pnpm invocation，不依赖 Extension SDK internal script；不拥有业务路由、readiness、打包或运行时生命周期。

Product package manifest 通过统一的 `product:prepare`、`product:dev`、`product:start` 原子入口声明开发准备与 Product Host 命令。Desktop 的准备链可调用 Desktop `prepare-runtime`；Personal Server 的准备链只调用共享 Contracts/Extension SDK owner task，不经过 Desktop assets。Supervisor 只消费这些显式 owner 入口，不维护按产品分支的业务表。

### 4. 依赖与交付边界

两个工具 workspace 不进入 runtime production dependency、deploy manifest、发布制品或 installed host。runtime/package/deploy manifest 不得依赖它们；工具自身不得依赖 root 命令完成逻辑。根 `scripts/` 三文件与 Extension SDK → Supervisor 反向 owner 泄漏在迁移完成后直接删除，不保留兼容 wrapper。

## Consequences

- Root 命令保持稳定，但实现 owner、测试与失败语义可独立演化。
- Repository invariant 与 owner 行为分离；新增合规工具不再触发 exact-count 架构失败。
- Desktop 与 Personal Server 保留同一 Supervisor 进程树语义，同时拥有各自 preparation chain。
- 增加两个 private workspace 与 lockfile importer；它们不构成发布 package 或运行时依赖。

## Alternatives considered

- **继续保留三个 root scripts**：文件少不等于 owner 清晰，且会继续固化数量快照；拒绝。
- **新增 `engineering/` 或 `automation/` 总桶**：只会把 root 混合区下移一层；拒绝。
- **让 Supervisor 维护产品准备表**：会重新成为业务组合事实源；拒绝，准备入口由 Product package 声明。
- **保留 root wrapper 兼容旧路径**：当前没有迁移窗口或外部 consumer 需要它；拒绝。
