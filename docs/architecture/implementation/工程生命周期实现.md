## 部署状态机

```text
acquire host.lock
  -> prepare
  -> replace / restart
  -> readiness
  -> bridge_readiness
  -> commit
  -> committed
```

`host.lock` 与 `.host.lock.guard` 的 inode/FD 必须保持一致。竞争返回 75；不可信路径、锁身份
替换或不能恢复操作前状态返回 78，并把 `recovery_action` 写入 transaction journal。Bridge
先生成 durable request 与 one-shot owner，等待其持锁 `ready`，compare-or-create 绑定
operation/nonce 的 ack，并观察到 `started` 后才返回 accepted。request/result/ack/decision
四件套共同裁决 timeout 与迟到 owner；owner 在 EXIT 写 `committed`、`failed`、
`recovery_required` 或 `owner_timeout`，结果可按 operation ID 查询并按终态 retention
整体清理。Bridge 只写 request、ack 与不可变 decision，绝不代 external owner 或稳定 recovery
authority 写 terminal result；无 owner 回执的超时证据保留而非伪造 `owner_timeout`。旧 Bridge 被回收不影响 owner 收口。Product HTTP/Web 只传递同一 operation ID，
重连后查询同一终态；失败状态不会映射成 HTTP 200 或 audit succeeded。

`status/logs` 不经过上述状态机。它们只读现有 env，并用当前权限查询 Docker；缺文件或
权限不足按稳定 exit 失败，不运行 sudo。

## 数据与制品

- backup 根按 manual/transaction/restore-safety 分离；transaction retention 不遍历其他根。
- Smoke 在临时目录复制 models/packages；任一 symlink 使准备失败并清场。
- DLQ replay 不接受任意命令；Kernel 注册 `kernel.event-bus.v1`，把原始 payload 交给
  `DlqReplayIngress`，只有全部 EventBus handler 成功且 Kernel owner 写入受限路径的 durable
  receipt 后才把记录标为 replayed。无 handler、任一 required/partial handler failure、receipt
  写入中断或 binding 冲突都会保留 envelope 以重试/调查。receipt 绑定 source/record/owner/event type/trace/payload digest/operation/
  dispatcher；legacy Cognition source 未注册并稳定失败闭合。
- prepare-runtime 把 lockfile、toolchain、共享/package manifest 与依赖任务的实际 output
  digest 纳入 cache identity，并比较每个 output 的 path/size/SHA-256。
- encoding CLI 以显式 repository root 或工具自身位置解析仓库，检查 tracked 与未忽略 inventoried text 的合法 UTF-8/BOM；architecture CLI 只拥有 root 拓扑、workspace/package、legacy 删除、依赖方向、derived/ignore 与平台角色硬编码等 repository invariant。Desktop、Personal Server、Audio、deploy 等行为断言留在 owner tests。
- Workspace Supervisor 自己解析 Windows Corepack/项目 pnpm 与 POSIX `corepack pnpm`，只监督开发期 Kernel/Product Host 进程树并原样传播 child exit。Desktop 和 Personal Server 分别通过自己的 package manifest 声明 preparation；后者不经过 Desktop asset task。
- Desktop staging 在调用 electron-builder 前准备 bundled Node、Python 3.12.13、由
  `products/desktop/runtime-python/uv.lock` 聚合解析的 Contracts/Cognition/Audio dependencies
  与 Kernel resolved dependencies，并验证 Kernel、Cognition、Audio、Avatar、Extension Host
  与 native 六类投影。隔离 Python 必须能导入安装后的 generated Contracts 并启动 Cognition
  module；安装态 resolver/supervisor 直接从 resources 启动这些固定运行时，installer manifest
  与组件文件逐项绑定。
- 两个产品的 manifest producer 与 integrity verifier 分离；可信 provenance 由 GitHub
  Sigstore identity 提供，Release 下载固定物料后重新验证。

验证入口是两个工具 workspace 的 `test`、root `pnpm test:tooling`、`deploy/personal-server/tests/test-host-transaction.sh`、
`products/personal-server/scripts/test-release.sh` 和 owner package test/typecheck。
