# 文档与知识工程

从读者要理解的问题或完成的任务开始，确定交付是说明、查表、操作、学习路径还是维护规则。
先看所属页及其直接事实源；只有入口/归属不清时才读 [docs 导航](../../../docs/README.md) 和
[文档架构](../../../docs/governance/documentation-architecture.md)。拼写、链接等局部修正直接执行，不重做知识地图。

## 建立可核验内容

- 对重要陈述标清当前实现、目标要求、迁移状态、建议或历史。从 manifest、Schema、公开 exports、实际 consumer、
  测试和环境核验；路径存在、类型声明或历史 PASS 不能证明接线、ready 或真实设备行为。
- 按本次问题追踪输入→owner→提交/投影→失败/退出。改一处名称后搜索它的调用者和文档消费者，
  不只替换索引；已删除的源文件先查真实接替者，而非把旧路径改成看似合理的新目录。
- 选择最接近读者目的的写法。上手路径要能得到一个可观察成果；操作指南给前置条件、命令、预期反馈、
  失败分支和恢复；技术参考给精确语义与来源；解释连接原因、边界和取舍。一个连贯任务可以跨越几种资料，
  不为四种类型各造空页，也不将所有专业方法搬入 Skill。
- 按具体内容确定维护 owner。常用上下文可短述后链接详情；同一精确字段表、命令副作用或验收流程保持一处。
  路由应带读者前往答案或可执行步骤，避免 docs→Skill→原 docs 的无效往返。
- 代码示例只使用已核验 API；命令核对真实工作目录、依赖、输出、退出码和副作用。示例路径显式为临时数据，
  不把模型/设备下载、外部消息、生产迁移或发布藏在“验证”中。无法运行时保留命令与缺失条件，不伪写 PASS。

## 编辑与验证

沿 [文档维护](../../../docs/how-to/文档维护.md)按变化选择正文、消费者、生成视图、摘要与检查；
不把维护步骤套到每个补丁，已通过的写后检查可按其输入复用。历史保留原结论与替代关系，不追溯改写接受证据。

静态门之外，实际沿一个代表请求走到结果：能否找到正确版本/owner、完成步骤、识别失败、恢复或退出；
评估是说明成果就核验因果与例子，是操作指南就运行受控步骤，是导航就检查完整读取路径。
涉及界面体验时使用 [glimmer-ui](../glimmer-ui/SKILL.md) 与真实渲染，格式通过不能代替内容和行为验收。

交付说明读者成果、已核实或仍未知的事实、内容迁移、实际验证和失效条件；
共同证据规则见 [测试与验收](../../../docs/how-to/测试与验收.md)。
