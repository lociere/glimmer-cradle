# 测试与交付

适用任务：选择验证范围、组织检查批次、运行阶段门、复用证据、交付结果或说明未验证风险。本页唯一拥有**验证选择**；任务如何组织片段见[开发工作流](开发工作流.md)，角色、资源与回报见[会话与任务编排](会话与任务编排.md)。不要用“类型通过”代替功能完成。

## 1. 选择原则与输入

验证以风险覆盖、反馈价值、证据完整和失效条件共同优化，而不是以减少命令为目标。每次选择应消费以下输入：当前固定或未提交状态、风险清单、自然收束点、受影响 owner/consumer、已有账本和环境条件。

- 先选能最快证伪当前关键假设、且能覆盖真实故障模式的检查；快速门不是每次编辑必跑。
- 把相互依赖的检查组织为一个批次，在自然收束点运行，避免既过早又重复地验证半成品。
- 需要跨包、跨进程、真实设备、打包、外部服务或生产证据时，补齐对应门；必要门不得因成本省略。
- `pnpm typecheck`、`pnpm build` 是 PR 最低门，在交付/PR 阶段运行，并不代表编码片段逐次运行；其他范围专属的最低门见第 3 节。

## 2. 检查批次与阶段门

| 时机 | 目标 | 选择内容 |
|---|---|---|
| 片段中途（仅触发时） | 证伪会放大返工的关键假设 | 最小可行的单测、schema、生成、编译、静态或平台检查。 |
| 自然收束点 | 确认完整片段可以被下一片段消费 | 受影响单测/lint/schema、受影响包 typecheck/build 与真实风险门。 |
| 跨包或阶段 | 确认组合边界 | 相关子系统集成、Playwright、生命周期或实机检查；按变化运行 root `pnpm typecheck` 与 `pnpm build`。 |
| 交付/PR | 确认可审查、可合并的固定状态 | PR 最低门及风险矩阵要求的检查。 |
| 最终里程碑 | 确认交付物整体 | 固定 commit 上与交付相关的全仓、打包和集成验收。 |
| 外部/生产 | 确认环境行为且可恢复 | 在单独授权、固定制品和回滚门下运行环境矩阵、发布与生产验收。 |

跨层架构、协议、生命周期、数据或安全的 candidate 必须覆盖真实故障门；低风险局部改动可在定向检查和自查后直接闭环。发布/生产门由唯一环境 owner 执行。

## 3. 特定最低门

除第 2 节按风险选择的批次外，以下变更保留其专属最低门：

| 改动 | 最低门 |
|---|---|
| TypeScript PR | `pnpm typecheck`、`pnpm build` |
| Cognition | `cd core/cognition; uv run pytest -q` |
| Audio | `cd engines/audio; uv run pytest -q`，必要时 health/warmup/synthesize/recognize |
| UI | 相关 desktop typecheck/build、Playwright，必要时 Electron 实机 |
| Contract Spine / SDK | 运行 `pnpm contracts:verify`，再运行 Service/Document/SDK 两端验证 |

## 4. 风险到验证

| 风险 | 必须补充 |
|---|---|
| runtime/lifecycle | 启动、ready、degraded、failed、restart、stop、子进程回收 |
| Schema / 跨进程契约 | 成功、缺字段、未知枚举、非法组合、生成/同步、旧字段搜索 |
| 数据迁移 | 备份、旧版本、损坏样本、重复迁移、回滚 |
| 权限、secret、不可逆副作用 | 拒绝路径、确认/撤销、幂等与失败恢复、脱敏 |
| Avatar | 透明、首帧、DPI、多显示器、拖动、动作、口型、打包版 |
| Audio | health、warmup、synthesize/recognize、timeout、process log |
| Extension/MCP | 注册、拒权、确认缺失、调用、断连、撤销、dispose |
| 可观测性 | trace、日志、metrics、DLQ、脱敏 |

Contract Spine 变更运行 `pnpm contracts:verify`；不要手改生成物，也不要让 owner-local projection 反向成为第二事实源。UI、Desktop、Avatar 和 Audio 的实机门不能由 renderer 或类型检查替代。

## 5. 验证账本与证据复用

验证账本记录：代码/依赖/环境状态，命令与范围，结果，证据位置，覆盖的风险，及失效条件。失败证据记录退出码、失败步骤和足以定位的相关片段；成功证据记录可复用状态和报告位置。

相同代码、依赖、环境和风险假设下的成功结果可复用。审查者默认只读增量 diff 并复用有效账本，不因“不放心”重跑昂贵成功门；只有 diff、依赖、环境、风险假设或明确验收门变化时补充检查。失败先定位根因；同一策略连续两次无效时停止，核对事实源并缩小问题。

## 6. 交付与未验证说明

交付必须包含完成行为、影响边界、已运行验证及结果、未运行验证及原因、真实剩余风险、账本/报告位置与已同步文档。若环境缺失，给出具体缺失项和可复现命令。

禁止通过放宽测试、吞错、改成 warn、保留假 fallback 或跳过 ready 检查让验证“通过”。例如 Avatar 打包版未验证时，要说明缺少的 Unity batchmode/目标 runtime、已运行的替代检查，以及 `host_ready` 与 native composition 的剩余风险；不能只写“未测试”。

验证若改变事实（例如 runtime 只能 degraded、默认值不同、打包路径已迁移），同步 Reference 或 Implementation；测试结论不能只留在对话中。
