# 文档、注释与编码

> 适用任务：文档、注释、术语、命名、编码风格和交付说明。
> 本卡提供文档实施方法；文档归属、质量标准和规范用语由 [文档维护规范](../../../../../docs/文档维护规范.md) 统一维护。

## 1. 确定文档归属

按信息职责选择唯一权威页：

- Blueprint：平台解释、架构审美、长期不变量；角色身份事实归 Character Profile。
- Current：当前结构、边界和运行关系。
- Implementation：代码入口、组装、状态机和调试链路。
- Reference：字段、配置、路径、日志、SDK 和打包映射。
- Guide：操作步骤、失败恢复、验证和文档同步。
- Roadmap：未完成成果、范围、风险和验收门。
- ADR：长期架构取舍。
- History：已结束阶段和被替代设计的证据。

正文页必须说明范围、事实依据和维护触发。Guide 还必须包含适用场景、前置条件、操作、失败处理、验证和需要同步的文档。

## 2. 编写正文与注释

正文采用客观、直接的技术书面语，按职责、条件、行为和结果组织。要求强度、事实与建议、比较方式和术语使用遵循文档维护规范中的“规范用语”。

注释用于说明设计理由、跨边界契约、不变量、生命周期、并发或平台限制，以及可删除条件。TODO 应明确责任主体和解决条件；迁移说明应给出适用范围与退出条件。

当前实现声明应依据代码、Schema、配置或测试核验。设计建议和待验证假设应显式标明状态；引用其他文档时使用其权威入口。

## 3. 编码与信息安全

中文正文和注释使用 UTF-8 无 BOM；代码标识符、协议字段、配置键、事件类型、扩展 ID 和文件名沿用既有英文命名。密钥、token 和 provider key 仅保存在授权的秘密配置或环境变量中。

新增或批量改写 `.ts`、`.tsx`、`.py`、`.yaml`、`.json`、`.md` 时，遵循项目 `.editorconfig` 并确认写入工具使用 UTF-8 无 BOM。PowerShell 的编码行为应按版本核对；批量修改后执行 `pnpm check:encoding`。

## 4. 迁移与质量检查

迁移前依据当前职责重新分类内容，再写入对应权威页。迁移后更新 Skill 路由、索引和引用，检查旧路径、术语一致性、规则冲突和相对链接。

正文质量按类型检查：Reference 应能查证字段、owner 和变更规则；Guide 应支持操作与失败恢复；Roadmap 应包含成果、边界、风险和验收门；Implementation 应指向真实代码入口与链路。

职责重合的正文合并维护；历史过程归入 History。删除页面前先更新引用，再删除被替代文件。交付时说明迁移范围、保留的历史证据和当前入口。

## 5. 命名一致性

Glimmer Cradle 的正式中文名为“微光摇篮”，上下文明确时可简称“摇篮”。文档正文使用中文解释；机器接口、代码标识符、包名、命令、Schema 和配置键保持英文稳定命名。Protocol、Kernel、Cognition、Extension、Skill Plane、Avatar、Presence、Engine 和 readiness 等术语保持一致。

新增或重命名标识符、目录、命令、Git 分支前，读取 [命名规范](../../../../../docs/guides/development/命名规范.md)。命名应表达职责和 owner；分支名表达工作性质与 scope。Runtime 适用于生命周期监督、语言/平台固定术语或第三方正式名称。跨文档使用的新术语应同步到 Current 术语表。
